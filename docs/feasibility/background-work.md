# Codex and background work

## Codex jobs

| Data | Source |
|---|---|
| Jobs, status, title, prompt | The Codex plugin's files under `<claude dir>/plugins/data/codex-openai-codex/state/<slug>-<hash>/`: `state.json` (the last 50 jobs of the workspace, short entries) and `jobs/<id>.json` and `.log` (one job, full). `<slug>` is the base name of the workspace's git root and `<hash>` the first 16 hex digits of the SHA-256 of its real path, so Rabe lists the folders instead of computing the name. The shared loop polls every 2 seconds while work runs. After five unchanged idle passes it polls every 10 seconds (see [the loop](../architecture.md#shared-poll-loop)). |
| Which session | `sessionId` in the job is the Claude Code session id (the plugin's `SessionStart` hook puts it in `CODEX_COMPANION_SESSION_ID`); compare with `$.session.id()`. `state.json` can hold a bare status patch without `sessionId`; the job file has it. `$.session.usage().startedAt` skips the folders whose `state.json` did not change during this session. |
| Status | `queued`, `running`, `completed`, `failed`, `cancelled`. `completedAt` and `startedAt` are ISO times. `summary` in the job file is the prompt's start; in `state.json` it is the result's first line once the job ended. `kindLabel` is `rescue`, `review` or `adversarial-review`. Only background jobs keep `request.model`, `request.effort` and `request.prompt`. |
| Model, effort, tokens per request | Codex's own session file `<codex home>/sessions/YYYY/MM/DD/rollout-<local time>-<threadId>.jsonl` (`CODEX_HOME`, default `~/.codex`; the folder date is local time). The job file has the `threadId`. Records: `turn_context` (`model`, `effort`, `sandbox_policy.type`), `token_count` (`info.last_token_usage`, one model request, and `info.total_token_usage`, the sum, each with `input_tokens`, `cached_input_tokens`, `cache_write_input_tokens`, `output_tokens`, `reasoning_output_tokens`). Tested: the file grows during the run, one `token_count` per step, so tokens update live. In 40 rollouts of 2026-10-09 the `last_token_usage` of the records whose total changed added up to the final total, and no record repeated a total; Rabe still counts a record only when its total changed. `cache_write_input_tokens` was 0 in all 5,903 records seen. Each record has a `timestamp`. The total counts the whole thread: in a rollout with three turns of 2026-10-06 it grew across turns (15,383, 34,741, 56,347 input), and the companion's `task --resume-last` starts a new job on the same thread, so its file holds the earlier jobs' turns too. The job file's `startedAt` came about a second before the first record of its turn (2026-10-09), so Rabe counts only records from the job's start on, and its tokens as the total less the total at that start. A finished job also stops at its `completedAt`: a later job that resumed the thread adds records after it, and Rabe can find the finished job only then. A finished job without `completedAt`, or a running one, reads to the end of the file. |
| Prompt | The first `event_msg` `item_completed` of type `UserMessage`. Also for foreground jobs, whose job file has no `request`. |
| Progress text | `response_item` records of type `message` with role `assistant`, text in `content[].output_text`. |
| Commands | `custom_tool_call` is written when a command starts; its `input` is a small script such as `text(await tools.exec_command({cmd:"git status"}))`, so the command is taken from `cmd`. `item_completed` of type `CommandExecution` (`command` as argv, `cwd`, `status`, `aggregated_output`, `exit_code`) comes about when it ends, then `custom_tool_call_output` with the same `call_id`, then `token_count`. `task_complete` comes last. There are no `exec_command_end` records. |
| Reasoning summaries | `response_item` of type `reasoning`, `summary[].text`, only when `model_reasoning_summary` is set in the Codex config (for example `concise`). Without it `summary` is empty and the reasoning is encrypted. We tested both. |
| File changes | `event_msg` `item_completed` of type `FileChange`: `item.changes` maps each absolute path to `{ type: 'add' \| 'update' \| 'delete', … }` (`content` for add and delete, `unified_diff` and `move_path` for update), with `item.status` (`completed`, `failed`) and the payload's `completed_at_ms`. A `move_path` that is not null would name a new path (all seen were null); Rabe then counts the old path deleted and the new one added. Rabe counts only completed ones. |
| Files a command wrote | Candidates from a `CommandExecution` with `exit_code` 0: the script of `command` (`["/bin/bash", "-lc", "<script>"]`), with relative paths taken against its `cwd` (a `file://` URL, decoded per path segment). A candidate counts when it is a file whose mtime lies between the record's `started_at_ms` and its `completed_at_ms` plus 2 s. |
| Who started a job | The plugin's `codex:codex-rescue` agent (plugin 1.0.6; the only agent it ships) forwards the request with one Bash call, `node ".../scripts/codex-companion.mjs" task [--write] [--model m] [--effort e] [--resume-last] "<prompt>"`, and returns its stdout. `/codex:review` and `/codex:adversarial-review` run the companion from the main session, and the plugin's stop-gate hook from a hook; neither is an agent. The job file names no agent, so Rabe links a job to the agent's Bash `tool.call` (`agentId`, the command line): a background launch prints `<title> started in the background as <job id>. Check /codex:status <job id> for progress.` on stdout; a foreground run prints its progress on stderr, among it `[codex] Thread ready (<thread id>).`, and the Bash result holds stdout and stderr. Its stdout is only Codex's final message. The job's `summary` (`shorten(prompt)`: spaces collapsed, cut at 96 with `...`) is in the command line when the prompt is; `startedAt` is set when the job starts, so a foreground job starts while the Bash call runs. `kindLabel` follows the subcommand: `task` is `rescue`. Read in the plugin 1.0.6 source (`codex-companion.mjs`, `lib/codex.mjs`, `lib/tracked-jobs.mjs`) and in forwarder transcripts on disk. |
| Resume a job's thread | `codex resume <thread id>`, the `threadId` of the job file. Rabe copies the command; it does not run it. |
| Cancel | `node <plugin root>/scripts/codex-companion.mjs cancel <id> --json --cwd <workspaceRoot>` through `$.process.run` (d.ts:3472). Set `CLAUDE_PLUGIN_DATA` to the plugin's data folder: without it the script looks in `$TMPDIR/codex-companion` and finds no job. The plugin root is `installPath` of `codex@openai-codex` in `<claude dir>/plugins/installed_plugins.json`. |

Limits of the link: a job started by a call that went to the background (`run_in_background`, or the 2-minute Bash timeout) links only by the prompt while that call runs, and a prompt passed in a file (`--prompt-file`) or through stdin links only through the thread id once the call returned. A job started by the main session's own companion call is not tracked as a call, so if it had the same prompt as a forwarder's call at the same time, the forwarder could take it until the call returns its job id or thread, or until the forwarder's own job shows too (two jobs fit, so neither is linked); the stop-gate hook's jobs have their own summary and never match. Without proof the forwarder and the job stay two rows.

Limits: Codex deletes old session files. Older jobs then show `n/a` for file data. Rabe keeps a byte cursor for each rollout and parses only new records. Files beyond the 4 MiB read limit catch up over several polls. A record larger than that limit is skipped. Such a rollout stays partial and has no cost estimate. See [incremental file reads](../architecture/reading.md).


## Background shells

| Data | Source |
|---|---|
| Command, task id | Bash `tool.call` input and result `backgroundTaskId` (d.ts:16032, d.ts:20215). Set for `run_in_background`, Ctrl+B (`backgroundedByUser`) and a timed-out command (`timedOutAfterMs`). |
| Output file path | The result `text`: `Command running in background with ID: <id>. Output is being written to: <path>.` Tested. |
| Output, exit code | `/tmp/claude-<uid>/<project>/<session>/tasks/<taskId>.output`. Live output, then an empty line and `[exited with code N]`, or `[killed]` for a stopped task. Tested. Read once with `$.fs` up to 4 MiB. New bytes arrive through `tail -c +N` with a session cursor. Larger output catches up over several polls. |
| End | `prompt.submit` with `origin.kind` `task-notification`. Its text holds `<task-notification>` blocks with `<task-id>`, `<tool-use-id>`, `<output-file>`, `<status>` (`completed`, `failed`, `killed`) and `<summary>` (`… failed with exit code 3`). Tested. The `UserMessage` row's `task` (d.ts:14467) has the same fields and `durationMs`, but only while the row is drawn. |
| Still running | `classic.Stop` `background_tasks` lists running work (`type` `shell` with `command`, `monitor`, `subagent`, `workflow`); a finished task is not in it. A Monitor tool task runs as a `local_bash` task, so it is listed as `shell` with a `command`; `monitor` is only an MCP or WebSocket monitor (checked in the 2.1.295 source, `local_bash: "shell"`, `monitor_mcp` and `monitor_ws: "monitor"`). |
| Port | Output first (`localhost:5173`, `127.0.0.1:8080`, `port 4000`). On Linux, a running shell without a port also uses `fuser <checked outputPath>`, `ps -A -o pid=,ppid=` and `ss -ltnpH`. Every socket owner must belong to the file holders or their descendants. |
| Stop | `TaskStop`. |

Rabe accepts only this temporary task layout with the current `$.session.id()` and the project folder encoded from `$.session.root()`. It checks the resolved file against the resolved task folder before reading. An unexpected path or a symlink outside that folder gives no output. Polls, notifications and Stop correction use this check.

The port scan runs every 6 seconds in the shared loop, after output polling. One `ps` and `ss` snapshot serves all shells in the scan. Each shell gets a fresh `fuser` lookup, so no cached PID can outlive its process. Commands use argument arrays and a 5-second timeout. `uname -s` limits the scan to Linux. Rabe does not read process arguments or environments.

A missing tool, denied call, failed exit or truncated result leaves the port `n/a`. Stderr also rejects a result. This includes an exit-zero `ss` netlink error. If `fuser` exits with code 1 and empty stdout, no process holds the file open. The poll skips that shell without recording a fault. `fuser` alone can print its exact file label on stderr. It does not accept `--`. Its path is a checked absolute task path.

The file-to-process link depends on Claude Code’s output descriptors. Pipe-backed output, daemonized children, containers and other network namespaces can have no matching host listener. Unknown ownership shows no port. The first port found stays until the shell ends, as with output detection. Desktop process access and a real mod session remain unverified for this scan.

### Foreground Bash calls and direct `codex exec`

A Bash call without `run_in_background` reaches the mod's `tool.call` hook, and `next(e)` returns only when the call ends (or Claude Code moves it to the background, then the result has `backgroundTaskId`). So the hook is the only live signal of a foreground command: it carries the command, `description`, `tool_use_id` and `agentId` of the call, but no task id and no output file. Rabe adds a running shell for the call after 2 s and ends it when the call returns: `done`, `failed` when the answer has `isError`, `stopped` when the answer has `deny` (refused), the result has `interrupted: true` or the call rejects. A call under 2 s gets its row only when it returns, already ended with its start and end, so quick commands cause no running flicker but keep a Timeline bar. A subagent's call keeps `parentId: agent:<agentId>`; foreground calls of a subagent have not been observed live. Rabe keeps the newest 50 ended foreground rows. They count toward the shared cap of 200 ended items but go first when it is full, so a burst of quick commands never pushes out ended agents, Codex jobs or workflows. A call moved to the background leaves only its background row.

A `codex exec` run directly in a Bash command has no Codex plugin job folder, so the Codex source never sees it. A foreground run shows as the call's running shell. A run the command detaches (`nohup codex exec ... -o <file> ... &`) returns at once, so Rabe parses the command line (`hooks/codex-exec.ts`: a command word `codex` followed by `exec`, the absolute file of `-o` or `--output-last-message`, a closing `&`; the call ends at `;`, `&&`, `||`, `|`, `|&`, `&`, a newline or `)`, and a `&` after the `)` of a group around the call still detaches it, past redirects and further `)`, as in `(codex exec ... ) > log 2>&1 &`; inside the group a newline, `;`, `&&`, `||`, `|` or `|&` does not leave it, so `(codex exec ...\n) &` is detached too, while a `&` inside the group (`(codex exec ...\nsleep 1 &)`) is not) and keeps the shell running until that file exists with a modification time not before the call. `codex` is a command word only when the words before it, back to the line start or a separator (`;`, `&&`, `||`, `|`, `&`, `(`, a newline), are unquoted assignments (`A=1`) or `nohup`, `setsid`, `exec`, `command`, `time` or `env`; after `env` also quoted assignments (`"A=1"`) and only the options `-i`/`--ignore-environment`, `-u NAME`/`--unset NAME`/`--unset=NAME`, `-C DIR`/`--chdir DIR`/`--chdir=DIR` and `--`; any other `env` option makes the line no launch, a conservative rule, since options such as `--null` or `--help` run no command. So `printf "value=" codex exec ...` and `echo codex exec ...` are none. One pass over the words finds it, so long lines stay fast. A result path with an expansion (`$VAR`, `$(...)`), in any of the three spellings, is not taken, since Rabe would poll the unexpanded name. One case is resolved: a line that starts with `NAME=/abs/path` alone, then `;`, `&&` or a newline, and then the call (`S=/tmp/run; nohup codex exec -o $S/out.md ... &`). `$NAME` and `${NAME}`, bare or in double quotes, then take that value. The value must be an absolute path of letters, digits, `_`, `.`, `-` and `/` only; any other command before the call (`cd /x && S=...`), a second assignment of the name, `||`, a prefix assignment (`S=/x codex exec -o $S/o`, which the shell expands before it assigns), single quotes or a backslash in the word leave the path unknown. A value set in an earlier Bash call is not known: Rabe reads no environment. A call that was refused (`deny`), failed (`isError`) or interrupted ends its row as stopped or failed instead of keeping it running, and a call Claude Code moved to the background (`backgroundTaskId`) leaves only its background row. Limits: a detached run that fails before it writes the file stays running. A detached run without an absolute `-o` file stays running until its session file records its end (see below).

The same parse reads the flags of the call (`codexExec`, for foreground and `run_in_background` calls and for rows Claude Code lists at Stop): `-m`/`--model`/`--model=` (the model), `-c`/`--config`/`--config=` with `model_reasoning_effort=X` (the effort, TOML quotes removed), `-s`/`--sandbox`/`--sandbox=` (the sandbox; `--dangerously-bypass-approvals-and-sandbox` and `--yolo` give `danger-full-access`), `-C`/`--cd` (an absolute directory) and an inline `CODEX_HOME=` before the call (a flag). Only a word without expansion counts, so `-m "$M"` and a quoted `"--model=$M"` or escaped `--mo\del="$M"` (flag named after quote and backslash removal, value unknown) give no model and void an earlier one and `-o $S/out.md` is dropped while the other flags still parse. A value must fit its allow-list (model `^[A-Za-z0-9][\w.:-]*$`, effort `^[a-z]+$`), or it is none. A `-p`/`--profile` makes the model unknown, since the profile may set it. Words from `--` on (the prompt) and every redirect operator with its operand (`<`, `<<<`, `>`, `>>`, `>|`, `>&`, `<&`, `<>`, `&>`, `&>>`) are not flags. The flags stay the same under `codex exec resume` and `codex exec review`. The result is the row's `detail.codex` facet (`model`, `effort`, `sandbox`); a command that names none of them still gets an empty facet. No separate prompt field is extracted; an inline prompt stays inside the stored command, which the detail view shows. The Cost view and the totals count such a run as a Codex worker: until its session file is matched, its tokens and cost are `n/a`, it adds to the unknown count and makes the Codex sum `n/a`, never zero.

#### Session file of a direct run

Tokens, cost, the thread id and the model Codex used come from the run's session file (rollout), the same file a plugin job has, read by the same code (`readSession`, `advanceRollout`, the price table). Tested with codex-cli 0.162.1 on 2026-10-15: `codex exec -s read-only --skip-git-repo-check -C <dir> -o <file> "..."` created `<codex home>/sessions/2026/10/15/rollout-2026-10-15T23-07-04-<thread id>.jsonl` within 0.3 s of the launch (file birth time). Its first record is `session_meta` with `payload.id` (the thread id), `payload.timestamp` (the start), `payload.cwd` (the `-C` directory), `payload.source: "exec"` and `payload.originator: "codex_exec"`. A Codex subagent's file has `originator: "codex_exec"` too, but an object as `source` (`{"subagent": ...}`), so only `source: "exec"` counts. The last record was `event_msg` `task_complete`. The first record holds the session's instructions (23 kB), so Rabe reads it with `head -n 1`, not the whole file. Codex prints a header to stderr, with the line `session id: <thread id>`.

Rabe finds the file in one of two ways:

1. **By the session id.** A foreground call (not detached) whose Bash result (stdout and stderr) has exactly one `session id: <uuid>` line keeps that id as `detail.codex.threadId`; the file is then found by name in the day folders around the start, as for a plugin job. Two different ids in the output give none. This needs stderr to reach the Bash result: a command that redirects it (`2> log`, `> log 2>&1`, as in the #152 example) hides the id, so for a foreground run leave stderr unredirected (`codex exec ... -o out.md - < brief.md`, without `2>`). A background or detached run's output never reaches the result, so it is matched by time.
2. **By time.** Without a session id, a run is matched once its window closed: 12 s after its start (`EXEC_AFTER_MS` 10 s plus 2 s for Codex to write the first record). A file fits a run when its `session_meta` start lies from 5 s before the run's start (`EXEC_BEFORE_MS`; a `run_in_background` row starts when the call returns, a little after the launch) to 10 s after it, its `source` is `exec`, and, when the command names an absolute `-C`, its `cwd` is that directory. Only files in the day folders around the start, changed since 5 s before the start, are read; a file another row already holds and a file whose thread a plugin job holds are left out. The run gets the file only when exactly one file fits it **and** no other direct run of the session fits that file. Otherwise the run is `n/a` (`detail.codex.isUnmatched`), decided once and not retried. When the command names a model (`-m`) and the file's `turn_context` names another, the file is not the run's: `n/a` too. A run started from a `cd` or another directory without `-C` is matched without the directory check, so a run of another Claude session or terminal in the same seconds makes it ambiguous, `n/a`, never a guess. Known limit: if the run's own Codex never writes a file (it fails before the session starts) and exactly one other `codex exec` starts within its window, that file is taken; `-C` and `-m` narrow this.

An inline `CODEX_HOME=...` before the call puts the file in another folder that Rabe does not search (Rabe reads only its own `CODEX_HOME`, else `~/.codex`, through `$.env.get`, never a process environment): such a run is `n/a` at once. A run whose row Rabe built at Stop from `background_tasks` has no start time and is not matched. A `codex exec resume` appends to an older file of an earlier day; it is found only by its session id within a day of the start, and only the records from 5 s before the run's start count.

Once matched, the row gets `tokens`, `costUsd` and in `detail.codex` the file's model, effort and sandbox (they replace the flags' values), `threadId`, `sessionPath`, `sessionUpdatedAt`, `isSessionPartial` and `sessionEndedAt` (the time of the last `task_complete`; a later `task_started` clears it). The file is read with the same byte cursor as a job's (state `rabe.rollouts`, keyed by the row id) while the row runs, and after its end until the file records `task_complete` or for 60 s. A gone or unreadable file makes the cost unknown. The 4 MiB read limit applies as for jobs.

**Status of a detached run without `-o`.** The Bash result says only that the launch returned. So the row stays running after the call returns (`detail.codex.isDetached`), and ends as `done` at the time of the matched file's `task_complete`. If no file is matched (ambiguous, none, inline `CODEX_HOME`), nothing can tell its end: the row ends as `done` when that is decided (at once for an inline `CODEX_HOME`), with `detail.codex.isEndUnknown`, and the facts line says `end n/a`. A run whose Codex stops without `task_complete` (killed, crashed) stays running, like a `-o` run whose file never appears. Records other than `task_complete` (such as an aborted turn) do not end it; they were not observed.

### A subagent's background tasks

Tested in the same spike: a subagent's background `Bash` and `Monitor` calls reach the mod's `tool.call` hook with the subagent's `agentId` (the Bash result has `backgroundTaskId`, the Monitor result `taskId`). Their `tasks/<id>.output` files are in the main session's `tasks` folder. Their end notifications go only to the subagent: the main session gets only the agent's own task notifications. So Rabe ends a subagent's shells and monitors from the last line of the output file (`[exited with code N]`, `[killed]`), and does not end them at the main session's `Stop` when `background_tasks` leaves them out.


## Monitors

Command, description, timeout and `persistent` come from the Monitor tool input and result (d.ts:16231, d.ts:20620). A monitor has no interval: it is one command that streams lines.

The result text (`Monitor started (task <id>, expires in …)`) has no file path. The output file sits beside the shells' files (`tasks/<taskId>.output`) and ends with the same exit line. Tested. Rabe takes the folder from a path it already knows; the end notification also carries `<output-file>`.

Notifications: each batch of lines arrives as a `<task-notification>` with `<summary>Monitor event: "…"</summary>` and `<event>` lines and no `<status>`; the end has `<status>completed</status>` and `Monitor "…" stream ended`. Tested.

Monitors use the same cursor rules as shells. Their output continues beyond 4 MiB. Unchanged files cause no content read or state write.

Line times: task notifications are delayed and often carry several lines, so their time is not when the line was written. Follow the monitor's output file instead, and label the times "received".

Rabe sees the last two only as a job gone from `session_crons` or `CronList`. |
