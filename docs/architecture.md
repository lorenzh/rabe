# How Rabe is built

Rabe has four parts. Sources watch hooks and files and turn them into items. The registry holds the items in `$.state`. The band and the pane draw the items. `hooks/register.tsx` connects the sources and the views and does nothing else; it hands the option `pricesFile` to `sources(on, file)`, which passes it to the agents and Codex sources.

```
hooks/
  register.tsx        calls sources(on, pricesFile), band(on), pane(on, hours)
  model.ts            item types (re-exported from the contract), itemId, mergeItem
  registry.ts         pure list changes: addItem, updateItem, endItem, capEnded, commit, pastEnd, prune
  sources/index.ts    Source type and sources(on, file), which calls each source
  sources/agents.ts   Claude subagents: items, live tokens and turns
  sources/workflows.ts  workflow runs: items, phases and their end
  sources/codex.ts    Codex plugin jobs: items, steps and /rabe-stop
  sources/shells.ts   background shells: items, exit code, port
  sources/monitors.ts monitors: items and their output lines
  sources/crons.ts    cron jobs and /loop wakeups
  sources/worktrees.ts  the repository's git worktrees, for the Effects tab
  tasks.ts            pure: task notifications, task output files, port guess
  writes.ts           pure: the files a shell command line may write, and whether a path changed
  prices.ts           pure: the price table, its lookup and the dollars of a request
  forwarders.ts       pure: the Codex companion calls of agents, and the jobs they started
  schedule.ts         pure: next runs of a cron expression
  testing.ts          test helpers: state in memory, files, core stubs
  ui/band.tsx         the band above the prompt
  ui/pane.tsx         the /rabe command, its pane and actions
  ui/builtin.tsx      hides Claude Code's own count of background work
  ui/render.tsx       one renderer: lines as row Boxes of Text and plain Buttons, charts as a Raster
  ui/view.ts          the view contract: Model, Size, Selection, Press, Line, Node, Drawn, View, Action
  ui/cells/           pure cell engine for charts (grid.ts) and the 256-color palette (palette.ts)
  ui/views/           pure views: band, pane frame, items, detail, cost, effects, timeline
  ui/*.ts             pure helpers: lists, facts, format
types/index.d.ts      the state contract: item types and the $.state keys
data/prices.csv       list prices per model, read at run time for the cost estimate (see docs/feasibility.md)
```

## The engine's rule for `$`

`claude plugin validate` and `claude plugin test` scan each module before it loads. The scan follows `$` only into functions declared in the same file. It refuses a module that passes `$` to an imported function, to a method of an object, or to a function held in a list. A state reference (`{ plugin: 'rabe', key: 'items' }`) or an atom must be written in the file that uses it.

This sets the shape of Rabe:

- Shared code is pure. `model.ts` and `registry.ts` never see `$`.
- Each file that writes items has its own small write loop (below).
- `sources(on)` calls each source by name. A loop over an array of sources is refused.
- A source gets `on`; the agents and Codex sources also get the user's price file (`pricesFile`). It imports the pure registry functions it needs.
- An event may have only one hook without a matcher in the whole module. A second one stops the module from loading. Sources therefore give each hook a matcher, also when it has to match every event (`{ cwd: /^/ }` or `{ isInteractive: [true, false] }` on `session.start`, `{ agentId: /^/ }` on `turn.step`, `{ stop_hook_active: [true, false] }` on `classic.Stop`). Hooks with matchers, also equal ones, may repeat. `prompt.submit` takes a real matcher, such as `{ origin: { kind: 'task-notification' } }`.

## The item model

One type describes everything Rabe tracks. It is written in `types/index.d.ts`, because the state contract must hold every type it names and must not import. `hooks/model.ts` re-exports it, so modules import item types from `./model` or `../model`.

```ts
type RabeItemKind = 'agent' | 'workflow' | 'codex' | 'shell' | 'monitor' | 'cron'
type RabeItemStatus = 'running' | 'done' | 'failed' | 'stopped'
type RabeTokens = { input: number; output: number; cached?: number }

type RabeItemOf<K extends RabeItemKind> = {
  id: string            // itemId(kind, nativeId): 'shell:bg_4c1e', 'agent:a1b2'
  kind: K
  title: string         // the one-line name lists show
  status: RabeItemStatus
  seenAt: number        // ms epoch, when Rabe first saw the item (set by addItem)
  startedAt?: number    // absent: started before Rabe loaded
  endedAt?: number      // set by endItem
  parentId?: string     // item id of the parent (a workflow, an agent); absent: main session
  tokens?: RabeTokens   // absent: n/a
  costUsd?: number      // dollar estimate from data/prices.csv (agents and Codex jobs); absent: n/a
  detail: RabeItemDetails[K]
}

type RabeItem = { [K in RabeItemKind]: RabeItemOf<K> }[RabeItemKind]
```

`kind` narrows `detail`. The details per kind:

| Kind | Detail fields |
|---|---|
| `agent` | `agentId`, `type?`, `model?`, `description?`, `transcriptPath?`, `cwd?`, `worktreePath?`, `worktreeBranch?`, `workflowPhase?`, `workflowIndex?`, `toolCount?`, `lastTool?`, `lastToolAt?`, `edits?` (`RabeEdit[]`, the newest 100 file changes, see below), `codexCalls?` (`RabeCodexCall[]`, the newest 10 calls of the Codex companion, see Forwarders) |
| `workflow` | `runId`, `taskId?`, `scriptPath?`, `transcriptDir?`, `phases?` |
| `codex` | `jobId`, `jobKind?`, `threadId?`, `model?`, `effort?`, `sandbox?`, `prompt?`, `workspaceRoot?`, `logPath?`, `sessionPath?`, `sessionUpdatedAt?`, `isSessionMissing?`, `isSessionPartial?`, `commandCount?`, `steps?`, `edits?` (`RabeEdit[]`, from the rollout) |
| `shell` | `command`, `taskId?`, `outputPath?`, `exitCode?`, `port?`, `portAt?` (when the poll found the port) |
| `monitor` | `command`, `description?`, `taskId?`, `outputPath?`, `timeoutMs?`, `isPersistent?` |
| `cron` | `jobId`, `prompt`, `schedule?`, `humanSchedule?`, `scheduledFor?`, `isDeleted?` |

A file change is `RabeEdit`: `{ path, at, via?, change? }`. `via` says how: `edit` or `write` (the tool), `shell` (a command line's candidate, checked on disk) or `codex` (a Codex file change, with `change` `add`, `update` or `delete`); a shell `mv` source or `rm` has `change: 'delete'`. An edit without `via` is an `Edit` or `Write` from before this field. The main session's changes have no item: they are the `$.state` key `rabe.edits`, the newest 100, written by the agents source.

An optional field that is absent means the data is not known. Views show it as `n/a`. A source that needs a new field adds it as optional to the contract, here, and in this table.

`model.ts` also has:

- `NewItem`: an item without `seenAt`, what a source passes to `addItem`.
- `ItemPatch`: the fields `updateItem` can change; `detail` is merged, not replaced.
- `EndStatus`: `done`, `failed` or `stopped`.
- `itemId(kind, nativeId)` and `mergeItem(item, patch)`. `mergeItem` always keeps the item's own `seenAt`, also when a full `RabeItem` is passed as the patch.

## The registry

The items live in one session value, `$.state` key `rabe.items`, an array in the order Rabe first saw them. It survives a hot reload. `registry.ts` has pure functions that take the list and return the next list. Each returns the same array when nothing changed. Values are compared with their object keys sorted, so `{ input: 10, output: 20 }` and `{ output: 20, input: 10 }` count as the same and cause no write:

| Function | What it does |
|---|---|
| `addItem(items, item, now)` | Appends a new item with `seenAt: now`. For a known id it merges the fields and keeps `seenAt`. |
| `updateItem(items, id, patch)` | Merges a patch into one item. Unknown id: no change. |
| `endItem(items, id, status, now)` | Sets `status` and `endedAt` on a running item. An item that already ended keeps its end. |
| `capEnded(items, max = MAX_ENDED)` | Keeps every running item and the newest 200 ended ones, newest by `endedAt`, else `seenAt`. Of two that ended at the same time, the one Rabe saw later goes first. `commit` applies it, so every write loop does. |
| `commit(held, change)` | Applies a change and the cap. Answers `{ items, dropped }`: the capped list to write and the ids the write drops, also one the change added and the cap dropped at once. Answers `undefined` when the capped list is the held list: nothing changed, or the cap drops what the change added (an old ended item a poll finds again), so a poll then writes no state. |
| `pastEnd(items, now)` | The end time an ended item takes when Rabe did not watch it end (a poll finds it): the oldest end of the ended items held, or `now` when there are none. `undefined` once 200 ended items are held, since the cap would drop it. So such an item never pushes out one Rabe watched. |
| `prune(record, dropped, items)` | A per-item record (`rabe.lines`, `rabe.turns`) without the entries of the `dropped` ids that are not back in `items`; the same record when nothing goes. Only those ids go: an entry a later write added stays. |

To list items, read the value: `const { value: items = [] } = await $.state.get({ plugin: 'rabe', key: 'items' })`. A read while drawing subscribes the drawing, so a write draws it again.

### The write loop

Every file that writes items declares `write` and `forget` at its top level (the scanner does not follow `$` across an import). `write` writes only when the list changed, and tries again when another hook wrote first. `commit` applies the cap, so any write can drop items; `forget` then drops the per-item state of exactly those items:

```ts
import type { EngineInterface } from 'claude-code'
import { type Change, commit, prune } from '../registry'

async function write($: Pick<EngineInterface, 'state'>, change: Change): Promise<void> {
  for (;;) {
    const { value, version } = await $.state.get({ plugin: 'rabe', key: 'items' })
    const next = commit(value, change)
    if (next === undefined) return
    const { isSet } = await $.state.set({ plugin: 'rabe', key: 'items' }, next.items, {
      ifVersion: version,
    })
    if (isSet) return forget($, next.dropped)
  }
}

async function forget($: Pick<EngineInterface, 'state'>, dropped: string[]): Promise<void> {
  if (dropped.length === 0) return
  for (;;) {
    const { value = {}, version } = await $.state.get({ plugin: 'rabe', key: 'lines' })
    const { value: items = [] } = await $.state.get({ plugin: 'rabe', key: 'items' })
    const next = prune(value, dropped, items)
    if (next === value) break
    const lines = await $.state.set({ plugin: 'rabe', key: 'lines' }, next, { ifVersion: version })
    if (lines.isSet) break
  }
  // the same loop for { plugin: 'rabe', key: 'turns' }
}

// in a hook:
const now = await $.clock.now()
await write($, items => addItem(items, item, now))
```

The library's `update($, atom, fn)` is not used: it writes even when `fn` returns the same value.

Per-item state outside `rabe.items` (`rabe.lines`, `rabe.turns`) must leave with its item, whether or not its output changed. That is done in the write itself, not in a hook on `state.set`: the live engine does not run the plugin's own `state.set` hooks for a write made in a `$.clock.every` or `$.clock.after` callback, so such a hook does not see the polls' writes. A write from a hook or a command does pass it.

`forget` removes only the ids its own write dropped, never every id missing from a list it read earlier: between the write and the pruning another write can add an item and store its output. It reads the list again right before each pruning and keeps an id that is back in it (an agent that resumed). Each pruning writes only when its value changed. The writers of `rabe.lines` and `rabe.turns` only set their own entry.

### Turns

The turns of a subagent live in a second session value, `$.state` key `rabe.turns`: an object from item id to a list of `RabeTurn`. They are kept apart from `rabe.items` so that the list stays small. Each turn is one model response of the agent:

```ts
type RabeToolUse = { name: string; summary?: string }   // 'Read', 'src/db.ts'
type RabeTurn = { index: number; at: number; text: string; tools: RabeToolUse[] }
```

`index` counts from 1 and keeps counting when old turns are dropped. `text` comes from `TurnStepResult.answer`. The source keeps at most 16,000 characters per answer with `clip`. A longer answer ends with `…`. The opened detail wraps all stored text as plain text. Bullet and numbered list markers stay with the first part of a long path. `summary` is the first of the tool's `file_path`, `command`, `pattern`, `path`, `url`, `query` or `description`, on one line of at most 80 characters. A longer summary ends with `…`. A `file_path` stays whole because the Effects tab tells files apart by it. Each item keeps its newest 30 turns. The turns of an item dropped from `rabe.items` go with it (see The write loop).

## The source contract

```ts
type Source = (on: On) => void
```

A source is a function in `hooks/sources/<kind>.ts` that registers its own hooks with `on`. Its hooks call `next(e)` unless they answer on purpose, and they never throw. To add a source, import it in `hooks/sources/index.ts` and call it in `sources(on, file)`:

```ts
export function sources(on: On, file: string): void {
  agents(on, file)
  shells(on)
}
```

A source owns the items of its kind. It uses `itemId(kind, nativeId)` for ids, so another source can set `parentId` without asking it. Test a source through the engine: raise its events in a test, and watch `rabe.items` with a test hook on `state.set`.

### Starting work: `session.start` with a matcher

`pane.tsx` owns the plain `session.start` hook. Each source gives its own start hook a matcher (see the rule above): the agents source uses `{ cwd: /^/ }`, and the Codex and worktrees sources use `{ isInteractive: true }`, since only a person at the prompt sees the band and the pane.

### Stopping an item

The pane stops agents, shells, monitors and workflows itself: it calls `TaskStop` through `$.tool.call` (see Actions under The pane). A Codex job has no task id, so it stops through a command instead. `/rabe-stop <item id>` is registered by the Codex source (with `immediate: true`, so it also runs during a turn). It answers with a matcher on the id prefix, `{ command: 'rabe-stop', args: /^\s*codex:/ }`, and returns `{ text }` that says what happened. The person can type `/rabe-stop codex:<job id>`. The pane's `x: stop` on a Codex job runs the same command with `$.command.run({ command: 'rabe-stop', args: <item id> })` and shows its answer as a toast, so the cancel stays in the Codex source.

## The sources

### Claude subagents: `hooks/sources/agents.ts`

One `agent` item per subagent, id `agent:<agentId>`. It covers agents the model starts, agents of workflows and teammates.

| Hook | What it does |
|---|---|
| `agent.spawn` | After `next(e)` gives the `agentId`, adds a running item: title from the description (else the type), type, model, the prompt (`detail.prompt`, cut to 600 characters), `startedAt`. A workflow agent gets `parentId` `workflow:<runId>` and `workflowIndex`; an agent started by another agent gets `agent:<parentAgentId>`. A refused spawn adds nothing. |
| `classic.SubagentStart` | Fires inside the spawn, before `agent.spawn` adds the item, so it adds a running item (title the agent type) when none exists; the spawn then merges its fields in. Sets `transcriptPath` (`<session>/subagents/agent-<id>.jsonl`, built from the hook's `transcript_path`) and `cwd`. It never sets `worktreePath`: a `cwd` that is not the session's may be the agent's worktree or a plain subfolder, and only the meta file or git tells them apart. |
| `turn.step` with `agentId` | After the response, adds its tokens (`input` is uncached input plus cache writes plus cache reads, `cached` is the cache reads inside `input`, the same as Codex counts them) and its price (`claudeUsd` of the usage's model, see The cost estimate) to `costUsd`, sets `model`, `toolCount`, `lastTool` and `lastToolAt`, puts the item back to running, and adds a turn to `rabe.turns`. Steps of loops Rabe has no item for (forks for compaction or memory) are ignored. |
| `tool.call` for `Edit` and `Write` | After the call, when it changed the file (`changedFile`: a result, no error, and not `staged` for review), adds `{ path, at, via }` to the agent's `detail.edits`, or without `agentId` to the main session's `rabe.edits`; the path from the result's `filePath`. A refused, failed or staged edit adds nothing. The Effects tab reads these, not the turns: a turn lists the calls the model asks for, which may be refused. |
| `tool.call` for `Bash` in a subagent, a Codex companion call | `companionCall(command)` (in `forwarders.ts`) finds a command line that runs the Codex plugin's `codex-companion.mjs` with `task`, `review` or `adversarial-review`. Before `next(e)` the agent's `detail.codexCalls` gains `{ at, command, text }` (the line cut to 600 characters, the newest 10 calls kept). After the call: a call moved to the background (`backgroundTaskId`, also a timeout) still runs and gets nothing; a refused one gets `endedAt`; one that ran, also with an error, gets `endedAt` and what `companionOutput` reads in its stdout and stderr: `jobId` from `started in the background as <id>.`, `threadId` from the progress line `[codex] Thread ready (<id>).`. The main session's calls are not kept (see Forwarders). |
| `tool.call` for `Bash` | Before `next(e)`, `beforeBash` stats the absolute candidates of `shellWrites(command, undefined, HOME)` (at most 20; `look` gives up after 1 s). After a call that ran to its end (`ranBash`: a result, no error, not interrupted, not in the background), `afterBash` stats them again and adds each path `changed(before, after)` names (after a failed stat, `isMissing` lists the parent folder: a listing without the name, or a parent that is missing by the same rule, makes the path missing; a listing that fails or still has the name, in any letter case or Unicode form (NFC), leaves it unknown; one listing per folder per look, inside the 1 s limit; error text is never read), `via: 'shell'`, to the agent or the main session as above. The call has no cwd, so relative paths are skipped (see feasibility). |
| `turn.complete` with `agentId` | Ends the item: `answer` is done, `aborted` is stopped, `refusal` and `error` are failed. Reads the meta file once more. |
| `session.start` | Runs the poll once, then every 3 seconds with `$.clock.every`. |

The poll reads `$.agent.list()`. It adds agents Rabe has no item for (started before Rabe loaded, or dropped by the cap). An ended one never gets a new recency: it takes `pastEnd`, the oldest end held, and is not added at all once 200 ended items are held, since the cap would drop it. So an unchanged list causes no write, however many ended agents it holds, and agents Rabe did not watch never push out the ones it did. The poll also ends items the list reports as `completed`, `failed` or `killed`. An agent can resume under the same id: when the list shows an ended item's agent as `pending`, `running` or `waiting`, the poll sets it running again and clears `endedAt`, and one the cap dropped is added back as running. `idle` does not count: a teammate is idle after each turn, which already ended its item. Then it reads the meta file of each running agent and copies `cwd`, `worktreePath`, `worktreeBranch` and `workflowPhase`. An agent with neither `cwd` nor `worktreePath`, or with only a `cwd` that is not the session's, shows its tree as `n/a`, not as the main tree. The meta file sits next to the transcript (`agent-<id>.meta.json`); for a workflow agent without a transcript path it is in the run's `transcriptDir`. The file appears about 1.5 seconds after the start and changes later, so the poll reads it each time.

Workflow agents are not in `$.agent.list()`: only `turn.complete` ends them.

### Workflows: `hooks/sources/workflows.ts`

One `workflow` item per run, id `workflow:<runId>`.

| Hook | What it does |
|---|---|
| `tool.call` for `Workflow` | After the call, takes `runId`, `taskId`, `workflowName`, `scriptPath` and `transcriptDir` from the result and adds a running item. A resumed run keeps its `runId` and runs again under the same item. Then it reads the script and stores the phase names of its `meta.phases` block in `phases`, in order, from strings and from the `title` of objects alike. A bracket inside a phase string (`'Review [fast]'`) does not end the list. A remote run has no `runId` and gets no item. |
| `prompt.submit` with origin `task-notification` | Reads `<task-id>` and `<status>` of each `<task-notification>` in the text (with `parseNotifications`; one prompt can carry several). When a task id is a run's `taskId`, it ends the run: `completed` is done, `failed` is failed, `killed` is stopped. |

The run's agents come from `agents.ts`; they point to the run with `parentId` and carry their phase in `workflowPhase`. A view gets a run's tokens by adding up its agents.

### Codex jobs: `hooks/sources/codex.ts`

Tracks the jobs that the Codex plugin (`codex@openai-codex`) starts for this session. Data sources and their limits are in [What Rabe can see](feasibility.md#codex-jobs).

- **Poll.** `session.start` (interactive only) starts `$.clock.every(2000)`. A tick while the last poll still runs is skipped, so a slow file system cannot pile up polls. Each poll lists the plugin's state folders, skips each whose `state.json` was not changed since the session started (`$.session.usage().startedAt`), and reads the rest. It keeps the jobs whose `sessionId` is this session's (`$.session.id()`), and checks that again in the job file, because `state.json` can hold a bare status patch without it. A job whose item already ended is not read again. For a finished job Rabe holds no item for, the poll first asks `commit` whether the item would change the list; when the cap would drop it again (it ended before every ended item held, so the cap dropped it before), its session file is not read and nothing is written. The other polls add only work in flight (`background_tasks`, `session_crons`), which the cap never drops.
- **Item.** `codexItem(job, session)` builds the item. Title: the first line of the job's `summary` (the prompt's start). Status: `queued` and `running` are running; `completed`, `failed` and `cancelled` end the item as `done`, `failed` and `stopped`, with `endedAt` from `completedAt`. Undefined fields are left out, so a merge never erases a known value.
- **Session file.** The rollout file is found once by `threadId` in `sessions/YYYY/MM/DD` of the start day and the day before and after (the folder date is local time), then kept in `detail.sessionPath`. It is parsed again only when its `mtimeMs` differs from `detail.sessionUpdatedAt`, so an idle job causes no write. Files up to 4 MiB are read with `$.fs.read`; larger ones with `grep -m 2` (turn context and prompt) and `tail -n 200` through `$.process.run`, and the item gets `isSessionPartial`. A finished job without a session file gets `isSessionMissing`; its model and effort then come from the job's `request`, when the job was a background job. An unchanged file gives no new fields, so the item keeps the model and effort the file gave. A file that cannot be read gives no `sessionUpdatedAt`, so the next poll tries again; the job still ends. `codexItem` sets `costUsd` from every session result except an unchanged file: a parse sets the new estimate, and a file that is gone (`isSessionMissing` at the end, or a known `sessionPath` that no longer stats while the job runs) or cannot be read sets it to unknown, so the last estimate never stays on a job that may have spent more. A failure in one job never stops the poll for the others.
- **`parseRollout(text, home, since, until)`.** Pure. `since` is the job's start (`startedAt`, else `createdAt`): a job that resumed a thread (`task --resume-last`) shares the session file with the jobs before it, so a record whose `timestamp` is before `since` gives nothing but the model, effort and sandbox of its `turn_context` and, for a `token_count`, the thread's total at the job's start. `until` is a finished job's `completedAt` (none while it runs or without the field): a record after it belongs to a later job on the thread and gives nothing, not even its `turn_context`. A record without a time counts as the job's. Reads model, effort and sandbox (`turn_context`), the prompt (first `UserMessage`), tokens (last `token_count` total, less the thread's total at the job's start; after earlier records with no total among them, unknown), `requests` (each `token_count` whose total changed gives its `last_token_usage` with the model of the last `turn_context` before it; a count missing leaves the request without a model, so without a price; a record without counts, `info: null` for rate limits only, adds none and leaves the last total in place), and the steps: assistant messages, reasoning summaries when present, finished commands (`CommandExecution`, with exit code and output line count), and a running command (a `custom_tool_call` that has no output yet). Steps keep the last 50, each text cut at 300 characters. `edits` (the newest 100, left out when none) are the paths of each completed `FileChange` (`via: 'codex'` with its `add`, `update` or `delete`) `checks` (the newest 100) are the absolute write candidates `shellWrites` finds in each `CommandExecution` with exit code 0 and a `started_at_ms`, against its `cwd`, with the command's run as `from` and `to`; a command with over 20 is skipped. `confirmed` stats each check when the session is read and adds a file whose mtime lies in the run (plus 2 s) to `edits`, `via: 'shell'`, sorted by time. A poll stats each path once for all its jobs (`Looks`), and all its checks share one 1 s deadline from the first check: a path whose stat has not come back by then (a stalled network mount) is left out, and the `FileChange` edits are still written. The `cwd` URL is decoded per path segment, so `%23` and `%3F` become `#` and `?`. Lines that do not parse (a line still being written) are skipped.
- **Cost.** After a full read of the session file `readSession` prices its `requests` (`codexUsd`) and `codexItem` sets `costUsd` to the result, also to `undefined`, so a sum from an older read never stays. A file read as head and tail misses requests between them and gives no price. An unchanged file is not read, so the item keeps its cost.
- **Forwarders.** After the jobs, each poll links jobs to the agents that started them (`linkForwarders` in `forwarders.ts`, one write only when a link changes). A job gets `parentId` `agent:<id>` only on proof: the agent's call named the job (`jobId`); or the job started (`startedAt`) at or after the call and, when the call returned, before its end, is of the call's kind (`task` is `rescue`, `review`, `adversarial-review`), and has the call's `threadId`, or, while the call names none, its title (the companion's summary of the prompt, without the `...` of a cut) is in the call's command line, compared without quotes, backslashes and extra spaces. Exactly one call may fit the job, and that call may fit no other job; else the job has no parent. Each poll decides every link again from the calls and jobs it holds, so a link the prompt made moves when the call returns a job id or thread of another job (the main session started a job with the same prompt, and it showed first), and goes while a second job fits. A forwarder that loses its job gets its row back. The views fold a pure forwarder into its job (see the Items tab).
- **Stop.** `/rabe-stop codex:<job id>` runs `node <plugin root>/scripts/codex-companion.mjs cancel <job id> --json --cwd <workspaceRoot>` with `CLAUDE_PLUGIN_DATA` set to the plugin's data folder. The plugin root is the `installPath` in `plugins/installed_plugins.json`. On success the item ends as `stopped`. Later polls skip it, so it keeps its cost only while its session file still has the `mtimeMs` the cost was read from (`sessionUpdatedAt`); a file that changed or is gone makes the cost unknown.

The codex detail fields are listed in the table above. `steps` holds `RabeCodexStep` values: `{ kind: 'message' | 'reasoning' | 'command', text, exitCode?, lines?, isRunning? }`.

The next three sources follow the work Claude Code runs as background tasks. Each writes items of its own kind only. The pure parsing lives in `hooks/tasks.ts` and `hooks/schedule.ts`, so views can use it too.

### Shells: `hooks/sources/shells.ts`

| Hook | What it does |
|---|---|
| `tool.call` `{ tool: 'Bash' }` | After `next(e)`: a result with `backgroundTaskId` adds `shell:<taskId>`, title the command. `outputPath` comes from the result text (`Output is being written to: …`). This covers `run_in_background`, Ctrl+B and a timed-out command. In a subagent, `parentId` is `agent:<agentId>`. |
| `prompt.submit` `{ origin: { kind: 'task-notification' } }` | Each `<task-notification>` with a `<status>` ends its shell: `completed` is done, `failed` failed, `killed` stopped. The exit code comes from the summary (`failed with exit code 3`). It reads the output file once more first, so a shell that ended between two polls keeps its last lines. |
| `session.start` | Starts a poll every 2 s. It reads the output file of each running shell, keeps its lines in `rabe.lines` (as the monitors source does), guesses a port (`localhost:5173`, `port 4000`) and keeps the time it found it as `portAt`, and ends the shell at the last line `[exited with code N]` or `[killed]`. | `classic.Stop` | A running shell missing from `background_tasks` ends by its exit line, else as stopped. A shell in `background_tasks` that Rabe never saw is added, without `startedAt`. A subagent's shells and monitors get no end notification in the main session: it goes only to the subagent (see feasibility). Their output files are in the main session's `tasks` folder, so the poll ends them from the file's last line, `[exited with code N]` or `[killed]`, as it does every shell.

### Monitors: `hooks/sources/monitors.ts`

The same four hooks for the Monitor tool, with the same `classic.Stop` rule for a subagent's monitor. The Monitor result has no file path, so `outputPath` is the sibling of a task output file Rabe already knows (`taskOutput`, tried again on each poll), or the `<output-file>` of the end notification. A subagent's monitor has no end notification in the main session, so it ends from its file once Rabe knows any task output path.

The end notification is handled only for task ids Rabe has as `monitor:<id>`: a shell's notification also carries an `<output-file>`, and reading it would file shell lines under a monitor id.

Monitor lines are kept apart from the item, in the `$.state` key `rabe.lines`: `Record<itemId, { seen, lines: { at, text }[] }>`. `seen` counts the lines read from the file; `lines` holds the newest 200, each with the time the poll first read it ("received"). A last line read while it was still being written (`hel`, then `hello`) is updated in place and keeps its time. The poll and the end notification both read the file, so the last lines are kept even when the notification comes first. Notification `<event>` lines are not used: they come late and in batches. The lines of an item dropped from `rabe.items` go with it, in the write that drops it (see The write loop), as its turns do.

### Cron jobs and loops: `hooks/sources/crons.ts`

| Hook | What it does |
|---|---|
| `tool.call` `{ tool: 'CronCreate' }` | Adds `cron:<id>` with `schedule`, `humanSchedule` and `prompt`. |
| `tool.call` `{ tool: 'CronDelete' }` | Ends the job as stopped and sets `detail.isDeleted` on a successful deletion. The list and detail label it deleted. |
| `tool.call` `{ tool: 'ScheduleWakeup' }` | Ends the running wakeup as done and adds `cron:wakeup-<scheduledFor>` with `scheduledFor` and no schedule. `stop: true` ends running wakeups as stopped. The `<<autonomous-loop-dynamic>>` prompt shows as "autonomous loop". |
| `prompt.submit` `{ origin: { kind: 'scheduled-trigger' } }` | Ends a wakeup due by now (plus 90 s, since a wakeup can fire early) as done only on evidence that it fired: the fired text is its prompt (a `/loop` wakeup fires its input verbatim), or its prompt is a sentinel such as `<<autonomous-loop-dynamic>>` and the text names it (the expanded dynamic tick tells the model to re-arm with that sentinel). Any other text ends nothing, also the expanded tick of a recurring `<<autonomous-loop>>` cron job, which names no sentinel. A wakeup whose tick Rabe does not recognise stays running until the next `ScheduleWakeup` ends it as done, or `stop: true` as stopped; it ends late, never early. |
| `session.start` | Calls `CronList` and adds the jobs made before Rabe loaded. |
| `classic.Stop` | Syncs with `session_crons`: a job gone from the list ends as done (a one-time job fired, a job expired); a new one is added. Wakeups are not ended here, and a listed job whose prompt matches a running wakeup is not added twice. |

`schedule.ts` has `nextRun(expr, from)` and `nextRuns(expr, from, count)`: the next times a 5-field cron expression matches in local time, after `from`. It reads `*`, numbers, ranges, lists and steps; day of month and day of week match either one when both are set, as in cron. Minutes advance in real time, so a next run is never earlier than `from`, also in the hour that repeats when summer time ends (a job in that hour can show twice). A broken or impossible expression gives `undefined` (an empty list). Claude Code adds up to 10 % jitter to recurring jobs, which this does not show. The band's next run (`nextAt` in `lists.ts`) and the cron detail use `nextRuns` too.

`writes.ts` has `shellWrites(command, cwd, home)`: the files a shell command line may write or delete, each `{ path, isDeleted? }`, the last change to a path winning. They are candidates: the callers check them on disk, and `changed(before, after)` says from two looks whether a path was written, deleted or left alone. It never throws and runs in linear time. `lex` reads the words with bash quoting and drops comments and here-doc bodies; a word keeps whether it has an expansion, whether it can become more or fewer words, and whether its first character is literal, which decides if it can turn into an option. Command substitutions are skipped as a whole with their own quotes and nesting (64 levels at most), so nothing in them counts. `simple` takes the redirections out of a command and unwraps the known prefixes; a keyword, `[`, `test`, `exit` or a group ends the walk. `targets` reads the operands of the table commands (`SPECS`: each command's short and long options); an option the table lacks, or a word that could expand into one, gives none. `shellWrites` walks the list: `&&` keeps going, `;` and a newline also commit, `||` skips its right side through the next semicolon or newline, then resumes, and a list sent to the background with `&` is dropped. An OR list with directory changes leaves later relative paths unknown. A later absolute `cd` followed by `&&` can establish the directory again. A newline directly after `||`, `&&` or a pipe continues that command. The rules and what is skipped are in `docs/feasibility.md`.

### Git worktrees: `hooks/sources/worktrees.ts`

Writes no items: it keeps the repository's worktrees in the `$.state` key `rabe.worktrees` (`RabeWorktree[]`: `path`, `branch?`, `isDetached?`, `isMain?`), so the Effects tab can place each changed file in the worktree that holds it.

| Hook | What it does |
|---|---|
| `session.start` `{ isInteractive: true }` | Runs `git worktree list --porcelain` through `$.process.run` (in the session's folder, 5 s timeout) at once and then every 10 s; a tick while the last run still goes is skipped. `parseWorktrees` reads the blocks: the first is the main worktree (`isMain`), `branch refs/heads/x` gives `x`, `detached` sets `isDetached`; a bare entry, a path git had to quote and a relative path are left out, and at most 100 are kept. The list is written only when it changed. A run that fails, cannot start (no git, the desktop), exits with another code than 0 (not a repository), is cut at 4 MiB or lists nothing writes nothing, so the last known list stays, and without one the views keep their behaviour from agent metadata. |

## The cost estimate

`hooks/prices.ts` is pure. `parsePrices(text)` reads a table in the format of `data/prices.csv` (see feasibility): it skips `#` lines, takes the next line as the header and keeps a row only when every rate is a number of 0 or more and `input` and `output` are set. `withOverride(base, own)` puts the user's rows first; a user's row that shares a name (ID or alias) with a built-in row of its provider replaces it and takes its names, so an override reaches every alias, except a name another user row of that provider names itself, which keeps that row's price; `findPrice(prices, provider, model)` takes the first row whose `model` or one of whose `aliases` is the ID. `claudeUsd(prices, usage, model)` prices one Claude response and `codexUsd(prices, requests)` a Codex job, the sum of its requests. Both share one rule per request: a prompt over `long_context_tokens` takes the `long_*` rates for every token when `long_scope` is `request`; a `session` scope, a missing rate or an unknown model gives `undefined`, never a guess. An empty cache column bills at the input price.

The agents and Codex sources each load the table with their own top-level `prices($, file)` (the scanner never follows `$` across an import): the built-in file under `$.plugin.root`, then the user's file first when `pricesFile` is set; a user's file that cannot be read gives an empty table, so every cost is `n/a`. The table is read when a price is needed, not kept: a module value would be one more thing a reload resets, and the read is small.

An agent's cost is the sum of its steps (`addCost`): the first step sets it, each later one adds to it, and one step without a price, an agent without `startedAt` (Rabe did not see it start) or tokens without a cost (counted before the cost, an item from 0.3.0 after a reload) leave it absent for good.

The views read `costUsd` only. `totals` in `lists.ts` sums the Claude agents and the Codex jobs apart; a worker without a cost, with or without tokens, makes its side and the whole sum `undefined`, since a smaller sum would read as the cost. Workers without tokens also count under the head's `n/a`. The detail's cost panel of a workflow follows the same rule for its agents. Costs are drawn `≈ $0.16` (`cost` in `lists.ts`).

### The view contract

Each view is a pure function from the model, the size and the selection to the lines of its body and its controls:

```ts
type Model = { items: RabeItem[]; turns: Record<string, RabeTurn[]>; lines: Record<string, RabeLines>; now: number; usd?: number; previous?: RabePrevious; edits?: RabeEdit[]; cwd?: string; worktrees?: RabeWorktree[]; sessionId?: string; removed?: string[] }
type Size = { columns: number; rows: number; surface: RenderSurface; hasInput: boolean; window?: { top: number; rows: number } }
type Selection = { tab: RabeTab; query: string; folded: string[]; selected: string; open: string; order?: RabeOrder; isFocused: boolean; isArmed: boolean; isListArmed: boolean; window?: RabeWindow }

type Span = [text: string, style?: { fg?: number; bg?: number }]
type Press = { key: string; label: string; action: Action; hotkey?: string; autoFocus?: true; dim?: true; bg?: number }
type Part = Span | Press                       // isPress(part) tells them apart
type Line = { spans: Part[]; right?: Span[]; bg?: number }
type Node = Line | { chart: Grid }

type ViewButton = { key: string; label: string; action: Action; hotkey?: string; autoFocus?: true; dim?: true }
type ViewInput = { key: string; label: string; placeholder: string; submitLabel: string; value?: string; isLive?: boolean; action: (text: string) => Action }
type Drawn = { nodes: Node[]; buttons: ViewButton[]; inputs?: ViewInput[]; toolbar?: number }
type Piece = Node | { button: ViewButton } | { input: ViewInput }   // layout(drawn): document order
type View = (model: Model, size: Size, selection: Selection) => Drawn
```

- **A line** is one row of the body: Text parts and plain Buttons, then a part at the right end. A view passes each line through `fitLine(line, columns)`, which makes it exactly `columns` cells wide, as a grid row was: parts cut with `…`, the right part at the end, spaces between, every character through `safe`, a Press with a `hotkey` counted with the `c: ` the engine draws before its label, and the line's `bg` moved onto each part, so two fitted lines can stand side by side. `beside(left, leftWidth, gap, right, rightWidth)` sets two columns of lines next to each other (the split, the Timeline's lower half).
- **A selectable row** is a line with one `Press`: a plain Button whose label is the row's name, keyed by a stable id (`row:<item id>`; a group header `group-<group>`; a tab `tab-<tab>`). The Effects tab's rows are not items, so their ids are their own: `row:file:<path>` for a file (it opens the agent that edited it last) and `row:ssh:<port>` for an `ssh -L` line (it copies the line). The other parts (marker, glyph, port, exit code, time) are Text. A row is one pressable thing: only Buttons take a press, so a row has no second control inside it. `itemLine(item, now, isSelected)` builds the Items row; the Cost, Effects and Timeline rows are built the same way.
- **Focus.** A Button takes no color. `dim` draws a name dim at rest and full under the focus or the pointer; the views dim every row but the selected one. The selected row also has an orange `▌` and the `selected` background, so it reads as selected while the pane does not hold the keys. `focusOn(lines, selected)` gives `autoFocus` to the selected row, else the first: the focus starts there when the pane takes the keys, and Enter presses it. Of several `autoFocus` elements the first drawn wins, so a view sets one.
- **The split shows no Buttons.** The detail beside the list goes through `plain`, which turns its Buttons into Text, so the arrow keys and Tab walk the list alone. The full detail (Enter) keeps its rows pressable (a workflow's agents).
- **Charts** (`{ chart: grid }`) are cells nobody presses: a Raster on the terminal, text lines elsewhere. Only the band uses one now. The Cost and Timeline bars and the time axis are block glyphs in Text parts of their rows: a chart is a whole node, so it cannot stand in a row beside the row's Button, and Text draws the same cells on the terminal and also on the desktop.
- **Controls.** `buttons` are drawn `[ label ]` in a row before the node at `toolbar` (the pane's toolbar, under the tab row), else after the body. The label carries the key (`x: stop`), since the engine does not draw hotkeys. Hotkeys are one digit or one lowercase letter. A control with `autoFocus` takes the focus (the detail's `b: back`). A control that cannot act now keeps its slot: `dim`, the action `NONE` (`{ type: 'none' }`, a press does nothing) and no hotkey, so the letter goes to the prompt as before. The list's `x: stop` and `g` (`g: stop group` or `g: stop run`) and the detail's `m: message` and stop are always drawn for the kinds that have them. A control of a detail that acts on an item names that item in its key; the list's `x` and `g` keep the keys `stop` and `stop-group` (see Target-bound keys). A stop never comes first: the list's toolbar starts with `s: search` (where the surface has `Input`), the detail with `b: back`, so the first element after the tabs is never a stop in any view (see The append-only focus order).
- `inputs` are drawn after the controls where the surface has `Input` (`size.hasInput`). A focused Input takes every key, also the hotkeys, so a view offers a control that focuses it (`s: search`, `m: message`) instead of focusing it itself.
- `Action` is what pressing does: `tab`, `open`, `fold`, `query`, `window`, `focus`, `stop`, `delete`, `remove`, `clear`, `copy`, `message` and `none`. `pane.tsx` runs it; the renderer never passes on `none`.

A new view is a file in `hooks/ui/views/` that exports a `View`. A new tab adds its view and label to `TABS` in `views/pane.ts` and its name to `RabeTab`. A new detail adds a case to `bodyLines` in `views/detail.ts`. Neither touches the renderer or `pane.tsx` unless it needs a new `Action`.

### The renderer

`render(ui, surface, drawn, act)` in `ui/render.tsx` is the one place that turns a `Drawn` (or its pieces, `layout(drawn)`, after `hold`) into elements, and it draws the same tree on every surface, in document order:

- Each line is a row `Box`. Its Spans are `Text` (color, background, `wrap="truncate"`), its Presses plain `Button`s (`plain`, `dimColor`, `hotkey`, `autoFocus`, `onPress`). A Button takes no color prop, so each run of parts on one background sits in its own `Box` of that color: the focused Button draws inverse over its label and the Box's background shows around it. A row with exactly one Button is keyed `line:<press key>`, which makes it the hover scope of that Button (`hover: { bold: true }`); an empty line draws one space so it keeps its height.
- A chart is a `Raster` on the terminal, keyed `cells` (the band's `band`), cut by `clamp` to the 512 columns and 256 rows a Raster takes. Elsewhere it is one `Text` per row: the desktop hands out a Raster that draws an empty Box, so the choice is `surface === 'terminal'`.
- Controls side by side in a row Box keyed `controls` (`controls-2` for a second run), and each Input where it stands. A press of an action `none` calls nothing.

### The palette

Every color in `palette.ts` is one of the xterm-256 colors 16 to 255, written as `0x00RRGGBB`: a cube color (each channel 0, 95, 135, 175, 215 or 255) or a grey (8 + 10n). Under tmux the engine reduces a hex color for a Box or Text to 256 colors with a coarse formula (`#203020` and `#402040` both became 59), so two dark backgrounds could fall together. `paint(rgb, surface)` therefore names a Box or Text color as `ansi256(n)` on the terminal, which the engine passes unchanged, and as hex on every other surface; `DEFAULT` (`0x01000000`) is no color, the terminal's own, so plain text and the background follow the person's theme. A Raster's cells keep the exact entry, which the engine's own reduction of Raster colors maps to itself. The 16 base colors are left out, since each theme draws its own.

| Name | xterm | Use |
|---|---|---|
| `dim`, `bright`, `grey` | 245, 255, 252 | Secondary text, emphasis, the cost chip |
| `orange`, `yellow`, `green`, `red`, `blue`, `purple`, `cyan` | 173, 179, 107, 167, 75, 176, 73 | Kinds and states (`tone`), group headers, ports |
| `selected`, `panel`, `raised`, `rule` | 238, 236, 235, 239 | Selected row, cost panel and summary line, the running turn, rules |
| `CHIP.*` | fg 216, 116, 150, 222, 117, 183, 210, 252 on bg 94, 23, 22, 58, 17, 53, 52, 237 | Band chips, legend, conflict and load notes: a light tint of the kind's hue on the dark cube color of that hue (`done` shares `workflow`'s) |

`palette.test.ts` checks that each color is an exact entry and that the colors drawn side by side (the text colors, the row backgrounds, the chip backgrounds and the chip texts) are distinct indexes, so tmux keeps them apart.

### The cell engine

A Raster is a fixed grid of terminal cells. Each cell is exactly `[codePoint, foreground, background]`: a code point is one printable width-1 BMP character, a color is `0x00RRGGBB` or `0x01000000` for the terminal's default. A Raster has no bold, underline or italic. It is a leaf: no press and no focus. Rabe draws only charts with it (the band); the pane is lines of Text and Buttons.

`hooks/ui/cells/grid.ts` builds such grids with plain functions and no `$`. They change the grid they are given and return nothing or the next column:

| Function | What it does |
|---|---|
| `grid(columns, rows, style?)` | A grid of spaces in the default colors (or the style's) |
| `safe(text)` | One cell per character: whitespace becomes a space; a character on the allow list stays; anything else becomes `?` |
| `clamp(g)` | The grid cut to the 512 columns and 256 rows a Raster takes; `render` applies it to every chart. The band passes its view a size within these bounds (`bounded` in `view.ts`) |
| `fit(text, width)` | Pads, or cuts with `…`, to exactly `width` cells |
| `write(g, x, y, text, style?)` | Text from `(x, y)`, clipped at the edge; a style leaves the colors it does not name |
| `spans(g, x, y, [[text, style], …], width?)` | Runs of styled text, the last cut with `…` at `width` |
| `wrap(text, width)` | Lines of at most `width` cells, split at spaces |
| `bar(value, max, width)` | A bar in eighths of a block (`█▉▊▋▌▍▎▏`), padded |
| `paste(g, src, x, y)` | Copies one grid into another, clipped |
| `encode(g)` / `decode(columns, rows, base64)` | The Raster `cells` string: little-endian u32 triplets in padded base64 |
| `lines(g)` | The text of each row, trailing spaces cut: the text fallback and the tests |

`safe` keeps an allow list, not a deny list: a deny list missed characters such as `☰` (U+2630), which the engine takes as wide and refuses, naming the cell's index, so the whole Raster is lost. The list holds code points terminals draw one cell wide: printable ASCII, Latin-1 letters and punctuation, Latin Extended-A and B, Greek, Cyrillic, general punctuation (no spaces, zero-width or format characters), currency signs, arrows, box drawing and block elements, and the glyphs Rabe draws outside those ranges (`GLYPHS`: `◐ ● ▶ ✗ ✓ ⚠ ⟳ ≈` …). Unassigned code points, marks, format and control characters in those ranges are out. Other scripts, emoji and symbols show as `?`. `fitLine` uses it too, so a line's width in cells is its length. `render.test.tsx` draws every character `safe` keeps in one Raster through the pinned engine, which checks each cell. A new glyph in a view goes into `GLYPHS`, or it shows as `?`.

### Sizing

`paneView` gives the tab's view `scroll.bodyRows` less the tab rows and their rule, the hint (1) and the rows its toolbar takes (`controlRows`: Buttons as `[ label ]` with a gap, wrapped at `bodyColumns`, plus one row per Input). It calls the view twice: once to learn its controls, once with the rows left. A body shorter than that is padded, so the hint sits at the bottom. A list longer than that is drawn whole: the pane is then taller than its body and the engine scrolls it, the focus carries the window along (see Focus and the arrow keys), and the wheel scrolls it. `size.rows` bounds the split preview. Every opened detail draws all recorded body lines for scrolling. The split preview keeps the newest lines that fit. It reserves one row for a hidden-text note and the Enter key that opens the full detail. Agent previews visit turns from newest to oldest and stop once the available rows fill. They wrap only a suffix bounded by the remaining rows times the text width. The note says `Older text hidden` without counting unwrapped lines. Other previews count the older lines they hide. With no room left below the facts the preview still draws its note. When the opened detail exceeds the available rows, its hint shows `↑↓ scroll`. Workflow rows keep `↑↓ move`. A workflow draws every agent row. Its head and top are never cut: a fact that wraps, such as an agent's transcript path in a short pane, scrolls like a list, in the full detail and in the split. No view cuts its lines to `size.rows`: what does not fit scrolls, so no row's Button is lost. `size.window` is the part of the view's rows the pane shows, from the Pane's `scroll` (`offset`, `bodyRows`); `paneView` moves its `top` up by the tab rows, the rule and the toolbar, so it counts in the view's rows.

The Items tab splits into list and detail side by side when `bodyColumns` is at least 90 (`SPLIT_COLUMNS`). A docked pane asked for 100 columns gets about 72 at a 200-column terminal, and an inline one at 100 terminal columns gets 96. Below 90 the list fills the width and ends with one summary line of the selected item on the panel background (`◐ review auth.ts · gpt-6.1-sol · ≈ $0.09 · 25k in · running`; a folded job's dollars and input tokens are its sum with its forwarder's, `withForwarder`, as in the Cost tab and the detail; an agent or job without a known sum shows `cost n/a` and no tokens), and Enter opens the full detail in place; `b` goes back. The list keeps an empty line between groups only when the whole list fits. In the split, a list longer than the pane scrolls, and the detail starts at the first row the pane shows (empty lines above it), so it stays in view beside the focus. That row is `size.window.top` moved just enough to keep the focused row in view (`shownFrom`): the engine follows the focus that way and does not ask again (see feasibility).

### The band

A `ui.render` hook on `AbovePrompt`. With no running item, or while a survey holds the band, it calls `next(e)` and draws nothing. Otherwise `bandView` draws an empty line, so the status line above does not touch the band, and one line of count chips, one per kind that has something to show, failed (ended in the last 10 minutes) first, then `claude`, `codex`, `workflow`, `shell`, `monitor` and `cron`, then the cost when any tokens are known. Each chip is `◐ 2 claude` in its kind's colors (`CHIP`); the cost follows, its dollar amount bright and the rest dim (`≈ $0.04 · 43k tok`). The amount is the session's cost from `$.session.usage().cost.usd`, as `/cost` totals it, when the host has one; else the sum of the items' dollars. The band never grows with the number of items. With a `maxRows` of 1 (a small terminal or a multiline prompt) it leaves out the empty line: a taller tree would give that row to the engine's `n more` mark and hide the chips. Names, ports and the next cron run are in the pane. Nothing in the band is pressed, so it is one chart.

The grid is `bodyColumns` wide and exactly as tall as its lines. The band before drew padded `Text` labels in a row; beside an open pane the band is narrow, a label wrapped its trailing spaces, and the band drew an empty line. The engine owns collapsing (ctrl+x ctrl+a); the hook gets no collapsed flag.

### The pane

`/rabe` opens the pane `rabe` with `closeOnEscape`, so Esc closes it; without it Esc only hands the keys back and the pane stays. The command cannot focus it (see feasibility), so `pane.tsx` opens it again with `focus: true` from `$.clock.after(1500)`, but only while `$.ui.panes()` lists it without the keys: a pane closed with Esc in that time stays closed. A resize that moves the pane between dock and inline takes its keys (see feasibility): the render hook keeps, per surface, the `placement` and `isFocused` of the last drawing in a module value (`seats`), and when the placement changed while the pane held the keys it calls the same late open after 500 ms. Until the pane holds the keys, the hint says "tab to select · esc close".

`paneView` draws the tab row as plain Buttons keyed `tab-<tab>` with the hotkeys `1` to `4`, which the engine draws as `1: ` before the label: `Items 7    Cost    Effects    Timeline` with `1-4 switch` at the right end at 90 columns and more, `Items 7  Cost  Effects  Timeline` below. No tab is ever cut off, since a lost tab would move every Button after it: where the labels do not fit, the gap shrinks to one, then the other tabs keep their first letter (`2: C`), and below that the tabs wrap onto more rows. The active tab is drawn full, the others dim, and a `━` line in orange under the active one, `1: ` included, marks it in the rule below the row (on one row only). Under the rule the toolbar holds the tab's controls and Inputs, then the body, then the hint. The desktop draws the same tree. Each value the pane keeps is a `$.state` key, so a hot reload keeps it:

| `rabe.selected` | The selected row's id (a click can select a row while the keyboard focus stays elsewhere; `ringOn` tracks the focus): set by a `ui.focus` that lands on a row, by a press that selects a row (a click, `selectsOnPress`), and by opening. An item id, or on the Effects tab `file:<path>` or `ssh:<port>`, which the other tabs do not find and so focus their first row |

#### Focus and the arrow keys

After a tab switch, `landView` reads the new view and hands it to `landing`. The ring visits the safe tab label first. It then moves to the view's `autoFocus` control or marked row. An empty view leaves the ring on its tab label. These plugin landings do not arm the list's destructive keys.

- **Focus follows the person.** A `ui.focus` hook on the pane stores the item id of the `row:` element the ring lands on in `rabe.selected`, so the detail beside the list, the summary line, the marker and `x`/`g` follow the focus without Enter. Enter presses the focused row: it opens the item (from the Cost and Timeline tabs too, in the Items tab). A click presses a row too, on the terminal in the fullscreen layout, but moves no focus ring. So the ring and the selection can part: focus A, click B, and B is selected while the ring stays on A. The pane keeps the ring's element apart from the selection (`ringOn`: where its `ui.focus` hook last saw the ring land, unknown after a reset). On the Items list a press on the ring's row or on the selected row opens it, and a press on another live row only selects it (`selectsOnPress`). Enter presses the ring's row, so it always opens: focus A, click B, Enter opens A. Only a pointer presses a row away from the ring, so a click selects first and opens on the second click: click B, click B opens B. A click on the focused row opens it at once. The press is the person's choice of that row, so it arms `x` and `g` for it (see Arming).
- **Arrows in a tall pane.** Where all rows fit, ↑ and ↓ move the focus row by row (the engine does it, and wraps). In a pane taller than its body the engine scrolls one row instead and leaves the focus. A `ui.scroll` hook answers such a move (no `pointer`, `|by| === 1`) with `{}`, so the window stays, and moves the focus to the next or previous row with `$.ui.focus`; the pane then scrolls to show it. The rows are the `row:` Presses of the pane's drawing in the held document order (`rowKeys` of `hold`, without the `gone` slots), and the step is `stepRow`: from no row, ↓ goes to the first row; past the first or the last row the hook passes the scroll on, so ↑ shows the tab row and ↓ the controls. The wheel (a `pointer`) and the page keys pass. The hook draws the pane's view again from state to know the rows; their keys do not depend on the width, since the split's detail has no Buttons. Group headers are not arrow stops; Tab reaches them.
- **A change of the view moves the ring.** The engine keeps the ring on an index, and a new view (another tab, the open item, the search, a fold) draws other elements there: Enter on the first Cost row, then a click on `1: Items`, pressed `[ x: stop ]`. So `act` in `pane.tsx` moves the ring after each such change with `$.ui.focus`, key by key, as `landing(action, open)` in `view.ts` names them: first the active tab's Button, which is always drawn and never moves, then the element the change leads to: `b: back` of the item opened, the row of the item gone back from, the group header folded, the Timeline's `w` control after it widened the window. A key the new view does not draw leaves the ring on the tab. The search keeps the ring in its Input, which never moves. Two calls also move the ring when it already sat on the second key at another index. While the pane does not hold the keys the calls are refused, and Enter goes to the prompt. Each such change also disarms the pane until a call lands (see Arming).
- **Presses run in a hook.** Rabe's own `$.ui.focus` from a Button's or Input's closure reaches none of Rabe's hooks (see feasibility), so the pane's `ui.focus` hook never saw a landing and every press that changed the view left the stops dim. So a closure only hands its action to the event it runs for, and the pane's `ui.press` and `ui.input` hooks (`carry`) run it beneath them and then carry it out with their own `$` through `act`, awaited, so a test's press settles with it. Events can be in flight at once (a plugin beneath may hold one open), so there is no shared slot: each event's hook adds its own slot, keyed by surface and element (`slotOf`), to a module map (`waiting`) before `next(e)`, and the closure, which the engine runs with the event's surface and element, fills the oldest empty slot of its element (`leave`). An event thus carries out only an action of its own element, and each action runs once. Two events on one element in flight at once may swap their actions, which are that element's either way. Their focus calls reach the `ui.focus` hook like the arrow hook's.
- **Back.** `b` in a detail goes back to the list, selects the item that was open and focuses its row (see above), since the ring would stay where `b` was. It selects the open item, not `rabe.selected`: in a workflow's detail the focus may have moved onto one of its agent rows, and `b` goes back to the run.
- **Keys.** On the list: ↑↓ move, Enter opens, `x` stop, `g` stop the group, `r` remove the selected row once it ended, `a` remove every ended row the search shows, `s` search; the hint names `x`, `g`, `r` and `a` only while they act. `g` stops the rows of the group the selected row is drawn in, as the search shows them: a held row that changed status stops with the group it stands in, not with the group of its status. When the selected row is a workflow or a workflow agent, `g` is `g: stop run` on that run instead, and `x` is dim: Claude Code stops a workflow only as a whole. Below the split the label of `s` keeps only the letter; `x: stop` and `g: stop group` keep their word. The hint under every tab names what works there (`↑↓ move · enter open · x stop · esc close`; on the Effects tab Enter on an `ssh -L` line copies it). In a detail: `b` back, `c` copy the command, prompt, agent id or resume command, `f` open the forwarder of a Codex job, `d` delete a cron job, `m` message an agent, `x` stop, `g` stop a workflow run. A workflow agent (`isWorkflowAgent`: its `parentId` is a `workflow:` item, or it has `workflowIndex` or `workflowPhase`) has no `x`, `m` or message field, since Claude Code can stop only the whole run and cannot message a workflow agent: its detail offers `g: stop run` on the parent run when that run can be stopped, and the list leaves it out of `x` and of a group stop. A letter no Button binds moves the focus to the prompt, and the next keys type into the composer; no hook can keep them (see feasibility).

#### The held order

If rows reorder while a row has the focus, the focus ring stays on the old index, so Enter presses another row (see feasibility). So the lists do not reorder while the pane is open. `/rabe` stores `orderOf(items)` in `rabe.order`: the item ids of each Items group sorted (running first, then the newest), the Cost list by tokens, the Timeline by start and the Effects files by `byConflict` (as `file:<path>`). Each list then goes through `stable(list, held, sort)`: the held ids first in held order, then the items Rabe saw since, in the order it saw them. On the Items tab a held item keeps its group when its status changes, and an item Rabe saw since the open goes into the group of its kind (AGENTS, SHELLS, MONITORS or CRON), also when it failed, so it never changes group either; it comes after the held rows of that group, in the order Rabe saw it. A new shell or monitor joins the block of the agent that started it. Such a row can stand above the focused row; the renderer seats it there and the pane moves the ring back (see Rows found later in a list). SHELLS and MONITORS are held in their family order (`byParent`), so the blocks drawn at the open are the held order. The Effects tab holds its files and its ports (`ports`: the shells that ran with a port at the open). Its files and ports found since the open follow the held ones in FILES and PORTS, in the order they were found (a file's first edit, a port's `portAt`), seated like the Items list's new rows. Opening the pane again sorts anew. Without `rabe.order` (nothing opened the pane yet) the lists are sorted on each draw. The held order is for reading: the rows stay where the person saw them. The focus is safe without it, since the renderer holds the focus order (see The append-only focus order).

#### The append-only focus order

The engine keeps the focus ring on an index in document order, not on a key, and `$.ui.focus` on the old key brings it back only when called after the new tree is drawn (see feasibility). So any Button, Input or Select that comes, goes or moves above the focused one while the pane holds the keys puts the ring on another element, and Enter acts on that one: it could stop the wrong shell. Fixing this per view missed case after case (NEW rows passing the controls, a workflow phase found late, the edit history cut at 100, a tab cut off at a narrow width), so the rule lives in the renderer, where no view can break it: **while the pane is open, the sequence of focusable keys it draws only grows at the end.** The one extension is the Items list and the Effects tab, whose new rows stand in their group or section; the pane then puts the ring back on its element (see Rows found later in a list).

- `hold(pieces, held)` in `render.tsx` takes the drawing in document order (`layout(drawn)`) and the keys drawn before (`Held`: key, latest label, control or row). It draws the held keys first, in their order: each element in place, or brought forward to its turn when the view moved it, or, when it is gone, a slot with the same key and its old label, dim, whose press does nothing (a row reads `gone name`, the word first so a cut keeps it; a control `[ x: stop ]` dim). A slot follows the element held before it, so it never stands under the heading of the next one (an Effects port's `:3000  serve` line). Then come the keys that are new, in document order: one drawn above a held one moves to just after the last held one; one already below stays. A line with several Buttons (the tab row) moves as one, so its keys never change.
- The layout makes this rare: the toolbar sits above the body, so rows found later end the order without passing a control; a control that cannot act stays as a dim slot; the tabs never cut a tab; the views keep their held list order for the reader.
- `pane.tsx` keeps the held keys per surface in a module value: a render hook may not write `$.state` (drawing is pure, and the host refuses the write), and the scroll hook reads them to step the arrows in the drawn order. The hold is for one view, its `scope`: the tab, the open item, the search, the folded groups and the Timeline window's hours. A change of these is the person's own, so the hold starts anew, and `act` moves the ring to a safe element (see Focus and the arrow keys). An open item that is pruned keeps the scope: the view falls back to the list, and the detail's keys stay as slots above it. `/rabe` clears the hold, and a reload of the hooks module empties it without telling the engine, which keeps the ring's index.
- `render.test.tsx` checks the rule with a seeded random walk on every tab and on the detail of a workflow, an agent, a shell, a cron job and a Codex job, on the terminal and the desktop: items come and go, change status and phase, edits leave the history, ports are found, the width and the selected row change, and after each step the keys drawn before are a prefix of the keys drawn now; on the Items list they keep their order, only rows and group headers come between them, and every tab and control keeps its index. Between steps the walk also presses a tab, a row, `b`, a group header or the search like the person: the view starts its hold anew, the first key of `landing` is drawn, and the element the ring lands on neither stops nor deletes. After each step the walk also checks what every focusable element acts on (its target: the items a stop stops, the item a delete or message acts on, the text a copy copies): a key never changes its target, and an index of the hold never acts on another target than it did before; the list's `stop` and `stop-group` may change theirs only on the person's focus on a live row, else the walk's arming, fed as `pane.tsx` feeds it, must hold them inert. The walk's person also focuses gone slots and group headers: such a focus never arms `x` and `g`, and while the selected row is gone they stay inert. The person also presses arrows that Rabe carries out (`step`, then a plugin's focus and `landed`), some refused, some onto a row that went meanwhile, some that a hook beneath sends onto another row or header and some that a hook beneath swallows (answers `{}` without `next`), as it does some of the person's own focus moves. The walk reads each move through `landingOf` from a trace that ends at the engine or at that hook: the selection follows the landing, `x` and `g` arm exactly when the move lands, as asked, on a live row, and a refused or swallowed move keeps the selection and disarms the pane. Its presses on another live row of the list select it and arm `x` and `g` for it, as a click does. A test walks every row of the list and finds one `x` and one `g`. A test checks that the first element after the tabs is no stop in any view. The four cases above have their own tests.

#### Rows found later in a list

A new item stands in the group of its kind (see The held order), so its row, and the head of a group that was empty, can come above the focused row. With `inPlace` (`seatsRows`: the Items list with no open item, and the Effects tab, whose new files and ports stand in FILES and PORTS) `hold` seats each new line that holds one row or group header Button where the view draws it: after the held key before it and the gone slots that follow that key. It never seats one above a held tab, control or Input, so these keep their index; a new control still goes to the end. The engine keeps the ring on its index, so a seated row above it moves the ring onto another row (see feasibility):

- The render hook compares the held keys before and after the drawing (`shifts`): when the element the ring sits on (`ringOn`) stands at another index now, it keeps that key in `shifted`.
- While `shifted` is set and the pane holds the keys, a press on a row or group header does nothing (`isHeldBack`): Enter would press the row that took the ring's index (on the Effects tab, copy another `ssh -L` line). A press while the pane does not hold the keys is a click, which presses what the person points at, so it acts. Hotkeys act on the selection, which no seated row changes, so they act as before.
- 100 ms after such a drawing, while the pane holds the keys, `regain` calls `$.ui.focus` on that key. A call made while the hook draws resolves against the tree before the one it returns, where the key still stands at its old index, so the ring stayed off its element (tested live). From the timer the call reaches no hook of Rabe's, so the engine's answer is the evidence: `{}` clears `shifted`; a refusal (for example `the move was abandoned`, when another drawing came first) counts as a refused landing and disarms, and the next drawing asks again, at most three times, and three times more each time the pane takes the keys back.
- A landing the pane's `ui.focus` hook sees (the person's Tab or arrow, Rabe's own moves) clears `shifted`, and a pending `regain` then does nothing, so it never undoes the person's move. A reset clears it too.
- `shifted` is a module value, like the hold: a reload drops it, and the reload already starts the pane disarmed.

`hold` with `inPlace` keeps the rule that matters for safety: no tab or control changes its index, and a key never changes its target; only rows and group headers, which open, select, fold or copy, move, and while one may have moved under the ring the pane holds their presses back. Elsewhere (the Cost and Timeline tabs, an open item) new rows still go to the end.

The hold alone does not make Enter safe: it keeps keys in place, and a key whose action follows the view, or a hold the pane starts anew while the engine keeps the ring's index, still lets Enter act on a target the person did not choose. Review found four such cases: an open item or a selected row that is gone, so the view falls back and a generic `stop` key keeps its slot with a new target; a landing another hook refuses while the pane keeps the keys; a reload that empties the hold; and, after such a fallback, a focus on the group header and back on the gone slot of the selected row, which armed `x` on the row the list fell back to, a row the person never chose and may not see. The rules: the keys of a detail name their target; the list's `x` and `g` act on the selection and arm only on the person's focus on a live row, so a selection that resolves through a fallback leaves them inert; arming covers what changes without the person. The random walk checks these rules on the views it reaches; it does not prove that no other case exists.

#### Target-bound keys

In a detail, every control that acts on an item carries its target in its key: `stop:<item id>` (`x`), `stop-run:<run id>` (`g` on a workflow run), `delete:<item id>`, `copy:<item id>` (a command, a prompt, an agent's id), `forwarder:<agent item id>` (opens the agent folded into a Codex job), `message-agent:<item id>` and the Input `message:<item id>`. A control that copies a resume command is keyed by the id it resumes, `resume:<id>` (a Codex thread in its job's detail, this session on the Cost tab, the previous session on the Timeline tab): a Codex job learns its thread after it started, so the key appears then, at the end of the focus order, and never changes what it copies. There the target changes only without the person (the open item ends or is pruned), so a new target is a new key: `hold` draws the old key as an inert gone slot and puts the new control at the end of the focus order. A slot that existed before never acts on another item.

The list's toolbar is the exception: `x: stop` keeps the key `stop`, `g` (`g: stop group` or `g: stop run`) the key `stop-group` and `r: remove` the key `remove`, and all three act on the current selection (`LIST_KEYS`). The person moves the selection on purpose with the arrows, Tab or a click, and a key per target would leave a dim slot in the toolbar for every row walked past. They arm only on the person's focus on a live row (see Arming). A target they gain without the person (the selected row or search result is gone and the list falls back to its first row, a row joins the group) disarms the pane; a row that leaves the group (it ended) only makes `g` stop less than the person saw, and keeps it armed, also when `g` can no longer act (`targetsOf` lists no target for a control without action).

Row Buttons stay keyed by what they show (`row:<item id>`, `row:file:<path>`): Enter on a row opens or copies and stops nothing. An Effects file row opens the agent that edited it last, which may change under the same key.

#### Arming

Destructive controls (stop, stop group, stop run, delete, remove, remove ended) act only while the pane is armed: the ring is known to sit on a safe element. Disarmed, `paneView` draws them dim, with the action `NONE` and no hotkey (`Selection.isArmed`), and the hint leaves out `x`, `g`, `r` and `a`. The logic is pure (`arm(state, event)` in `view.ts`); `pane.tsx` keeps the state in a module value and feeds it the events, and redraws when it flips:

- Disarm on `/rabe` (the open), on every change of the view through `act` (tab, open, back, fold, search: each has a `landing`), on a drawing whose open item or selected Items row is gone and the view falls back (`fallbackOf` in `views/pane.ts`, `open:<id>`, `selected:<id>` or both; once per new fallback), on a drawing whose list `x` or `g` gains a target (`targetsOf` in `view.ts`: one entry per control and item) while the stored selection `rabe.selected`, which only the person changes, stayed the same (the render hook draws the view armed to learn the targets, then again disarmed if it must; the first drawing after a reset takes its fallback and targets as given, since the landing that follows accounts for them), and on a `$.ui.focus` of Rabe's that is refused (`{ deny }`), throws or lands on another element than it asked for: `land`, the arrow hook and the `s` and `m` controls all go through one `focusOn`.
- A reload of the hooks module starts disarmed: the state lives in module memory, which is what a reload resets, the same memory as the hold.
- The list's `x`, `g` and `r` need more (`isListArmed`): the person's focus on a row the list draws live (`isLiveRow`: not a gone slot). The person's focus on a gone slot makes them inert; a focus on a group header, a tab or a control, a landing and `autoFocus` leave them as they were, so after a reset they stay inert until the person moves onto a row. While the selected row is gone (`selected:` in the fallback) they stay inert in every drawing: the row they would act on is one the list fell back to, not one the person chose. Each reset and each disarm above also makes them inert.
- Where the ring landed: a hook beneath Rabe's may send a `ui.focus` onto another element (`next({ ...e, element })`), refuse it, or answer `{}` without `next`, which keeps the ring where it was. The pane's `ui.focus` hook reads the landing from `next.trace` with `landingOf`: only a last link of Claude Code's own (tier `core`, the engine, or `builtin`, bundled in the binary, where the test kit's own hooks stand in for the engine) whose outcome is `returned` is evidence, and its `received.element` is where the ring landed. A move without that evidence, or refused, counts as refused: the selection goes back to what it was before the move, and the pane disarms (`landed` not moved). The selection follows a landing: a row stores its id in `rabe.selected`; another element keeps the selection from before the move. The hook writes the asked row before `next`, so the drawing during the move shows it, and puts the selection right after. The `focus` event carries the asked element (`requested`), the landed one (`key`) and the stored selection. A move that lands elsewhere than asked is nobody's choice: `x` and `g` go inert, and the pane disarms when it landed on a destructive element. `x` and `g` arm only while `rabe.selected` names the landed row. `focusOn` counts Rabe's call as moved only when the hook saw it land on the asked key (`landedOn`), so a rewritten, swallowed or refused landing or arrow disarms.
- A press that selects a live row of the Items list (`{ type: 'press' }`) arms `x` and `g` for it (`isListArmed`), but not the ring: a click leaves the ring where it was, and a later Enter presses the ring's row, which opens it (see Focus follows the person). Only a surface raises `ui.press` (a click, Enter, a hotkey; a plugin's `$` has no press), so a press is the person's.
- Arm on a `$.ui.focus` of Rabe's that landed where it asked, and on a `ui.focus` on the pane that no later hook refused, swallowed or sent elsewhere: by the person on any element, also a stop they chose, or by Rabe on an element that is not destructive (`isDestructive`: `stop`, `stop-group`, `remove`, `clear` and the prefixes `stop:`, `stop-run:`, `delete:`).
- A focus is the person's when the engine stamps it so (`origin.kind` `person`: Tab, an arrow where all rows fit, a click that moves the ring), and also the one move Rabe makes only to carry out the person's arrow in a pane taller than its body: the arrow hook feeds `{ type: 'step', key }` before its `$.ui.focus`, and the next `ui.focus` onto that `key` counts as the person's although it arrives with origin `plugin`. The next `focus` or `landed` event clears the step, so it covers that one move: a move that lands on another element (a hook rewrote it), a row gone before the move lands (not `isLiveRow`), a refused or throwing call, and every later focus of Rabe's (the landings after a change of the view, `autoFocus`, the `s` and `m` controls) stay Rabe's and never arm `x` and `g`. A reset drops the step too.

Limits: arming knows where the ring was put, not where it is. It relies on the hold: once armed, the drawings that follow keep every held key at its index, so the ring stays on that element until a reset, a fallback, a list target the person did not choose or a reload, which all disarm. A press by click or hotkey does not need the ring and acts on the live control the person sees, but `UiPressArgument` does not tell a click from Enter or a hotkey, so a disarmed stop is inert for a click too. While the pane does not hold the keys (a click gives it none), every landing is refused: after a change of the view by click, stop and delete stay dim until the person gives the pane the keys and moves the ring. The engine's own moves that raise no `ui.focus` (a reorder of rows Rabe never does, a resize between dock and inline, which takes the keys) are not evidence either way. Disarmed, `x` is not bound, so the letter goes to the prompt, as for any dim control.

#### The tabs

Copy actions pass the original text to `$.ui.copy`. A success toast replaces each run of whitespace with a space. A failed copy keeps the original text in its fallback toast so the person can select it.

**Items tab.** Groups: failed first, then agents (Claude, Codex, workflows), shells, monitors, cron; an item found while the order is held goes into the group of its kind (see The held order); inside a group running items first, then the newest (as held). A Codex job follows the agent that started it, after that agent's other jobs (`nest`), and is indented two cells under it, or under that agent's job before it. While the order is held a job keeps its held place, and a job found since joins its agent's block like a new shell (see Rows found later in a list). An agent that only forwarded to the Codex companion (`isForwarder`: it made at least one companion call, every tool call it made was one (`toolCount` equals the calls; an agent from before Rabe loaded has no count and stays), and a job is linked to it) has no row: `shown(items)` leaves it out of the Items, Cost and Timeline lists, the held order and the band's count, and its job stands for both. While the pane is open a row that folds stays as a `gone` slot (see The append-only focus order). A group header is `▾ AGENTS`: the arrow in the group's color, the name a Button that folds the group (`▸` when folded), and a dim note (`2 claude · 1 codex`, `2 running`). A row reads marker, glyph (colored by `tone`), the name as its Button, a shell's port and exit code, and the time, or the status word and age once it ended, at the right end. The selected row has an orange `▌`, the `selected` background and a plain time; other names and times are dim.

`byParent(list, items)` in `lists.ts` groups shells and monitors by who started them: the main session's first (title `''`, drawn without a header), then one block per agent in the order of its first item in `list` with the agent item (for its glyph) and its title, `run › agent` for a workflow agent and `agent n/a` for an agent Rabe no longer holds. In SHELLS and MONITORS the Items tab draws each agent's block under a header that is Text, not a row: the agent's glyph in its `tone` (a dim `◐` for `agent n/a`) and its title in dim. The children's rows are indented two cells after the marker. The list order, the first row that takes the focus and `rowKeys` follow the drawn order, so the arrows walk the children where they stand. The blocks are cut from the held order. A shell that came after the open joins its agent's block, after the block's held rows; the pane moves the ring back when that puts a row above the focused one (see Rows found later in a list). A failed shell stays in FAILED without its agent. The band counts the shells and monitors of agents with the others.

**Detail per kind.** The detail has three parts. `detailView` draws them in full. `detailLines(model, item, rows, width, sel?)` builds the split preview (`summary` in `views/items.ts`). The head (`headLines`) is the glyph, the title, the status word on the right, and the fact lines in dim. The top precedes the body: a cost panel and the brief or prompt, or the label of the body (`▸ output`, `▸ next runs`). The full detail keeps every body line (`bodyLines`). Only the split preview cuts older lines and marks hidden text:

- Agent: the facts add `agent <id>` and, last, `transcript <path>` (`n/a` without one) in full: `Facts.long` is cut into lines of the detail's width (`headLines(model, item, columns)`), never with `…`, so the agent file's name at the end of a long path shows, and `c: copy id` copies the agent id (in the running session `m` messages and resumes an agent). A cost panel (background `C.panel`): `≈ $0.16   in 36k  out 5k  cached 12k`, then `45% of session` and, while it runs, `active 3s ago` from `lastToolAt`. Then `▸ brief` with the prompt the agent was given, or the description for an agent Rabe did not see spawn (at most three lines, cut with `…`), then the turns from `rabe.turns`: `1  ● text` (index dim, `●` orange), then `⎿ Tool summary` per tool. The last turn of a running agent has the raised background `C.raised`. An agent that ran before Rabe loaded has no turns and says so.
- Codex: the facts say model, effort and sandbox, the job id, the thread id (`n/a` until the job file has one) and whether the session file was read, is partial (a file over 4 MiB, the last 200 lines) or is gone. With a thread id, `c: copy resume` copies `codex resume <thread id>`. A job folded with its forwarder says `forwarded by claude <title> · its tokens count here` instead of `started by`, its cost panel adds the forwarder's tokens and dollars (`withForwarder`; tokens, cached tokens or dollars that either side lacks make the sum unknown, never the other side's part), and `f: open forwarder` (key `forwarder:<agent item id>`) opens the forwarder's own detail with its turns, id and transcript. The forwarder has no row, so `b: back` from it selects its job's row (`rowOf` in `lists.ts`). The cost panel adds the command count and takes `active` from `sessionUpdatedAt`. Then `▸ prompt`, then `detail.steps`: `●` (cyan) messages, `thinking:` reasoning summaries, and `$ command` with `✓ exit 0 · N lines`, `✗ exit N` or `◐ running` on the right; the running command is raised. `x: stop` cancels the job through `/rabe-stop` (see Stopping an item).
- Workflow: the cost panel sums the run's agents and counts them. Then the phases as `✓ Review → ◐ Verify → · Report`, and per phase its agents in start order with their tokens and time (`22k · 40s`). The start order is held like the Timeline's (`stable` with `rabe.order.timeline`), so an agent that ends never moves under the focus. In the full detail each agent row is a plain Button that opens it, `b: back` keeps the one `autoFocus`, and the arrow keys walk the agent rows like a list: the row that holds the focus is selected and marked (`▌`, the `selected` background), the others are dim. The full detail draws every agent row, not the newest that fit; the pane scrolls.
- Shell: `▸ output · newest last · N lines` (`1 line` for one) (N is `seen`, all lines read), the lines in `rabe.lines`, and at the end `✓ exit 0` in green or `✗ exit N` in red once the exit code is known.
- Monitor: `▸ lines received · newest last`, each line after the time the poll first read it.
- Cron: `▸ next runs`, the next five times from the schedule with a countdown (`10:55  in 3:00`); a `/loop` wakeup shows `▸ fires` and its one time. Only running items show future times. Delete shows for cron jobs only: a wakeup has no id `CronDelete` knows. An ended job keeps its delete control in place, dim with no hotkey or action.

Cost, tokens and the share of the session left the fact lines for the panel; the spend there is the same sum the Cost tab uses. Cron runs seen this session and the per-tool exit codes of agents are not shown: no source records them.

**Cost tab** (`views/cost.ts`). A head row on a panel: the session's cost (`Model.usd`, from `$.session.usage().cost`, as `/cost` totals it; `session cost n/a` without it), the Claude and Codex estimates (`totals`, `n/a` when a worker of that side has no estimate), tokens, the running count and the number of workers without tokens; under it `session <id>` (`Model.sessionId`, from `$.session.id()`), with `c: copy resume` in the toolbar, which copies `claude --resume <id>`. Then a row per agent and Codex job (a folded forwarder's tokens and dollars in its job's row, `n/a` when either side lacks them), sorted by tokens when the pane opened (held): marker, glyph, the name as a Button that opens the worker in the Items tab, a bar in eighths of a block scaled to the largest, tokens, cost and run time. The bar takes the kind's chip color while the worker runs, green or red once it ended, and `▏` in dim where tokens are `n/a`. The header says "sorted by tokens when opened" when an opening order is held. New workers follow the held rows. Without a held order, the header says "sorted by tokens". Under **LOAD**, running agents that look slow, from `rabe.turns`: `◷ long tool` when the last step asked for tools 2 minutes ago or more (the tool still runs), `⚠ stuck` when the last step asked for none and no step came for 5 minutes. The foot names where the session cost comes from and says when a Codex session file is gone.

**Effects tab** (`views/effects.ts`). `touched(items, edits, cwd, worktrees)` in `lists.ts` collects the changed files of three kinds of editor (`Editor`): each agent's `detail.edits` (the `Edit` and `Write` calls that changed a file, not the calls a turn asks for, which may be refused or staged, and its shell writes checked on disk), each Codex job's `detail.edits`, and the main session's `rabe.edits` (`Model.edits`, editor `main session`). With git's worktrees (`Model.worktrees`, from `rabe.worktrees`) each file belongs to the worktree whose path is the longest prefix of its path (`treeOf`; paths compare through `isInside` and `pathKey` in `model.ts`, so a Windows path matches whatever its slashes and letter case, and one file under two spellings is one row), whoever changed it, the main session included, and is shown relative to that worktree. Without them, or for a file outside every worktree, a path is shown relative to the editor's worktree, `cwd`, Codex `workspaceRoot` or the session's `cwd` (`Model.cwd`). A long path loses its start, so the file name stays. A file two editors changed under one absolute path is a conflict (`isConflict`), also the main session and an agent: the tab heads with `⚠ conflict  src/logger.ts is edited by A and B in the main tree` on a red background (`in <worktree>` names a tree only when it is proven to hold the file: the worktree git places it in, `the main tree` for git's main worktree, or the worktree of an editor (Claude Code's metadata) whose path contains it; else the banner names no place), and lists conflicts first, then the newest changes (`byConflict`, held while the pane is open). A relative path is never a conflict; no source records one today, so this only guards against a stray tool result. Each row says who changed the file and how: the count when more than one (`3×`), then `edit`, `write`, `via shell` (checked on disk) or `codex add`, `codex update`, `codex delete`, and a red `deleted · ` when the last change deleted it. Every source records absolute paths only (a shell write's relative path is skipped, see feasibility), so the row has no mark for an unknown folder. Each file row is a plain Button on the file name that opens the agent or Codex job that changed it last, or copies the path when that was the main session; the selected one has the `▌` marker and the focus. Two worktrees never share an absolute path, so the same file in two worktrees is no conflict. Then WORKTREES (`worktreeRows`), one row per worktree in use, `⎇ name  branch · who`, and the header counts these rows. With git a worktree is in use when a file in it changed (its row names the editors, the main session included) or an agent runs in it: its `worktreePath` when git lists that path, else its `cwd`, unless it changed a file in some worktree, which already places it. The main worktree reads `main tree`. An agent worktree git does not list keeps its row from the agent's metadata, after git's. An agent in a subfolder of a worktree (its `cwd` only) sits in that worktree's row, never in a row of its own. Without git the rows come from agent metadata as before: each agent worktree, then `main tree` for the agents whose `cwd` is the session's and that have no worktree. Last, `n/a` counts the agents whose tree is not known (no `cwd`, with git a `cwd` outside every worktree, without git a `cwd` that is not the session's). Then the ports of running shells, each with its `ssh -L` line as a plain Button that copies it. A port has one row however many shells report it (`portsOf`), since two rows with one key would trap the arrow keys on the first; the row names the first shell that has it. While the order is held, FILES and PORTS show the rows of the open in held order, then the files first edited and the ports found since, in the order Rabe found them. A port whose shell ended leaves the view; while the pane is open its `ssh -L` row stays as a `gone` slot (see The append-only focus order). The first port's line has a background and the hotkey `c`, which the engine draws as `c: ssh -L …`. The tab has no controls. Every file is a row and the tab scrolls: a file list cut to the rows the other sections leave would gain or lose Buttons above the `ssh -L` lines whenever a port, a worktree or a conflict came or went.

**Timeline tab** (`views/timeline.ts`). The tab shows a window of time, `sel.window` (`RabeWindow`). `/rabe` sets it to the last `timelineHours` hours (the `userConfig` option, default 4; `hoursOf` reads it, `0` is no limit, anything that is not a number of hours is 4) and writes it to `rabe.window`. Its start `since` stays put while the pane is open, so the window grows with the time and no row folds away under the focus. Items that ended before `since` fold into one line of plain Text, `+37 older items, ended before 10:20`, above the rows: not a row, so it holds no Button and the focus order of the rows stays. Running items and items that ended inside the window stay rows; a bar that starts before the window is cut at the left edge and starts with `◂`. Who started what lists the same items. The control `w` (key `window`, before `c: copy resume` in the toolbar; neither is a stop) steps the window for the open pane, `widen`: base hours, 12 hours (when the base is less), the whole session, then base again; a wider step never starts later than the one before. Its label names the next step (`w: show 12 h`, `w: show all`). A step is the person's change of the view, so the hold starts anew, the pane disarms, and `act` lands the ring on `tab-timeline`, then `window`. With the option at `0` the window is the whole session and the tab has no `w`. The Items and Cost tabs show every item either way. Then a head with the window (`last 40 min`, `last 4h05m` from two hours on), a legend of chip colors and a time axis of round clock times and `now`: at most four labels, spaced 1, 2, 5, 10, 15 or 30 minutes or 1 to 24 hours apart as the window needs, each placed where its time falls (`10:20  10:30  10:40  now`). A label that would repeat the one before it or run into it or into `now` is left out, so a short window never names one minute twice. One row per item in the window, sorted by start when the pane opened (held): the name as a Button that opens it, then a bar from its start to its end (or now) in the kind's chip color while it runs, green or red once it ended. A cron job draws a tick at each scheduled run since Rabe saw it and before it ended, computed with `nextRun`. The legend says "scheduled run". Actual firing times, idle delays and jitter are not recorded. A space parts the name, cut with `…`, from its bar. Below: who started what (`tree`, with the kind in brackets for all but Claude agents; a forwarder stays in it, with its job under it), and the previous session in this project (`Model.previous`): side by side from 90 columns, else one under the other. The previous session ends with ` id <session id>`, `n/a` for a summary without one; with an id, `c: copy resume` in the toolbar copies `claude --resume <id>`.

### Removing ended items

The list keeps every item until the cap drops it (200 ended items), so a long session fills it with finished work. `r: remove` (key `remove`, action `remove` with the selected item) hides the selected row once it ended; `a: remove ended` (key `clear`, action `clear`) hides every ended row the search shows. Both are drawn always, dim while they cannot act (a running or no selected row; no ended row), and nothing running is ever removed.

- **State.** `remove($, action)` in `pane.tsx` adds the ids to `rabe.removed` with the versioned retry of the write loop (`ifVersion`; two removes in flight read the same value, and a plain write would bring one row back) and toasts what went ("Removed shell bun run lint", "Removed 4 ended items"). For `clear` it takes the ended items at the press, from `rabe.items` and the search in `rabe.query`. The items stay in `rabe.items`: a poll that finds an ended item again (a task output file, `CronList`) adds or merges it in the registry, and its id still hides it, so nothing comes back. The pane and the band pass every item and `rabe.removed` (`Model.removed`) to the views, and only the rows go: the Items list and its count, the Cost and Timeline rows, the agent rows of a workflow's detail and the band's chips leave the removed items out through `kept(items, removed)`, so the arrow keys and Enter never reach a removed row. Everything that sums up keeps them, so removing never makes history false: a workflow's phases with their counts and tokens, the Cost tab's totals, the cost line in the band, the Effects tab, and the order `/rabe` takes. An id whose item is running again (an agent that resumed) shows again, since `kept` never hides a running item. An id stays after the cap drops its item, since a poll may find that item again; the value is session state, so it survives a reload and starts empty in a new session. The previous-session summary counts every item, removed or not, except cron jobs that ended before the session.
- **Focus.** While the pane is open, a removed row is gone from the view, so the hold draws its gone slot (see The append-only focus order): dim, and a press does nothing. When it was the selected row, the list falls back and `x`, `g` and `r` go inert until the person moves onto a live row (see Arming).
- **Arming.** Both keys are destructive: they act only while the pane is armed. `r` acts on the selection like `x`, so it also needs `isListArmed`, and it is in `LIST_KEYS`: a target it gains without the person (the selected row ended, the list fell back) disarms, as for `x` and `g`. `a` acts on no selection but on "every ended row", the same target whatever ends meanwhile, so it needs only `isArmed`, and its key keeps its target in the walk of `render.test.tsx`.

### The previous session

On `session.end` (`{ reason: /^/ }`) `pane.tsx` keeps a summary of the session in `$.store` under `previous:<cwd>`: `previousOf(items, now, usage, sessionId)` counts the items per kind (cron jobs still running only) and holds the tokens, the session's cost and start, the titles of failed items and the id `claude --resume` takes (`e.resume.id`, else `e.sessionId`) (`RabePrevious` in `types/index.d.ts`). `sessionId` is optional: a summary of Rabe 0.3 or older has none and shows `n/a`, and a value that is not a string is dropped when read. The Timeline tab names the scope of each figure, since they differ: `session ≈ $0.32 · 1h12m` is the whole session's cost (`cost n/a` when unknown) and duration, main session included, and `background 800k tok` is the tokens of the background items only. The stored record keeps its shape, so summaries of Rabe 0.3 and 0.4 read the same and need no migration. A session without items keeps the last summary, so a short session with no background work does not hide the one before. The pane reads the key on each draw; a value of another shape shows as no previous session. After `/clear` the summary is the cleared conversation's.


**Live updates.** `session.start` starts `$.clock.every(1000)`, which calls `$.ui.invalidate('ui.render')` while any item runs.

**Actions.** Stop calls `TaskStop` with the task id (shells, monitors, workflows) or the agent id, and runs `/rabe-stop <item id>` for a Codex job. Delete calls `CronDelete` only while the current job is still running. Refusals show plain text without the tool error tags. Remove and remove ended write `rabe.removed` (see Removing ended items). Message calls `$.session.send` to the agent. Copy calls `$.ui.copy` on the surface that was pressed; when it fails (no clipboard, or a terminal over SSH without OSC 52) the toast shows the text to select: `Copy failed: <reason>. Select it: <text>`. Each answers with a toast: "Stopping …", "Stop refused: …", "Stopped 7 of 9; 2 had already finished", "Message sent to …".

### Hiding Claude Code's own count

Claude Code shows background work itself: a pill in the hint under the prompt (`2 shells, 1 monitor · ↓ to manage`) and a part of the line that ends a turn (`· 2 shells, 1 monitor still running`). Rabe's band shows the same, so `ui/builtin.tsx` hides both. It is on by default; the `userConfig` option `hideBuiltinTasks` in `.claude-plugin/plugin.json` turns it off, and `register` then does not call `builtin(on)`.

- `PromptHint`: `stripTasks(hint)` splits the hint at ` · ` and drops the parts that only count work (`2 shells, 1 monitor`, `1 background agent`) and `↓ to manage`. The hook passes the rest on with `next({ ...e, props: { ...e.props, hint } })`, so the PR number, `esc to interrupt` and the other parts stay. Rewriting the whole hint would drop them. The mode label (`⏵⏵ auto mode on`) is not part of `hint` and stays. ↓ still opens Claude Code's background manager.
- `TurnDuration`: the "still running" part is not a prop, so the hook draws the line itself (`✻ Brewed for 5s`, dim, one empty line above) while Rabe knows of a running shell or monitor and of no running agent or workflow. While an agent or workflow runs, the engine draws "Waiting for …" without that part, so the hook passes. The own line leaves out what has no prop: `done 1:16`, a token budget and "messages hidden".
- The agent list under the prompt stays: no component and no setting hides it (see feasibility).

Both views are tested on the `terminal` and `desktop` surfaces. Tests feed the session values with test hooks on `state.get`, fix the time with `mock.clock`, and read a drawing with `screen(ui)` from `fixtures.ts`: each row Box as one line, a Raster decoded, each control alone. The views can also be called directly with a model, since they are plain functions: `gridOf(drawn)` lays a view's lines into a grid as the terminal does, so `views/*.test.ts` check the text and the colors at positions. The test kit cannot answer a plugin's `$.ui.focus` (the call fails, as a refused one does), so the pane's tests check that the arrow hook keeps a one-row scroll and passes the rest, that a change of the view leaves the stops disarmed, that a person's `ui.focus` (raised by the test) arms them, that a plugin loaded beneath Rabe (`plugins` of the test, `append` tier) that sends the move onto another row, refuses it or swallows it leaves the selection on where the ring is and `x` and `g` inert, and that a press on another row selects it and arms `x` for it while a press on the selected row opens it; `view.test.ts` checks `stepRow` and `arm`, also the events the arrow hook feeds (`step`, the plugin's focus, `landed`), since the kit runs no hook for the plugin's own `$.ui.focus`.
