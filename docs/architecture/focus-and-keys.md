# Focus and keys

### The pane

`/rabe` opens the pane `rabe` with `closeOnEscape`, so Esc closes it; without it Esc only hands the keys back and the pane stays. The command cannot focus it (see feasibility), so `pane.tsx` opens it again with `focus: true` from `$.clock.after(1500)`, but only while `$.ui.panes()` lists it without the keys: a pane closed with Esc in that time stays closed. A resize that moves the pane between dock and inline takes its keys (see feasibility): the render hook keeps, per surface, the `placement` and `isFocused` of the last drawing in a module value (`seats`), and when the placement changed while the pane held the keys it calls the same late open after 500 ms. Until the pane holds the keys, the hint says "tab to select · esc close".

`paneView` draws the tab row as plain Buttons keyed `tab-<tab>` with the hotkeys `1` to `4`, which the engine draws as `1: ` before the label: `Items 7    Cost    Effects    Timeline` with `1-4 switch` at the right end at 90 columns and more, `Items 7  Cost  Effects  Timeline` below. No tab is ever cut off, since a lost tab would move every Button after it: where the labels do not fit, the gap shrinks to one, then the other tabs keep their first letter (`2: C`), and below that the tabs wrap onto more rows. The active tab is drawn full, the others dim, and a `━` line in orange under the active one, `1: ` included, marks it in the rule below the row (on one row only). Under the rule the toolbar holds the tab's controls and Inputs, then the body, then the hint. The desktop draws the same tree. Each value the pane keeps is a `$.state` key, so a hot reload keeps it:

| Key | What it holds |
|---|---|
| `rabe.tab` | The selected tab |
| `rabe.query` | The search text; matches title, kind, command, prompt, description and agent type |
| `rabe.folded` | The groups folded in the list |
| `rabe.selected` | The selected row's id (a click can select a row while the keyboard focus stays elsewhere; `ringOn` tracks the focus): set by a `ui.focus` that lands on a row, by a press that selects a row (a click, `selectsOnPress`), and by opening. An item id, or on the Effects tab `file:<path>` or `ssh:<port>`, which the other tabs do not find and so focus their first row |
| `rabe.open` | The item whose full detail shows; `''` shows the list |
| `rabe.order` | The list order taken when the pane opened (`RabeOrder`, see The held order) |
| `rabe.removed` | The ids of ended items the person removed this session (see Removing ended items) |
| `rabe.window` | The Timeline's window (`RabeWindow`: `base` hours from the option, the `hours` shown and their start `since`), set by `/rabe` and by `w`; absent, the pane takes the option's |

#### Focus and the arrow keys

After a tab switch, `landView` reads the new view and hands it to `landing`. The ring visits the safe tab label first. It then moves to the view's `autoFocus` control or marked row. An empty view leaves the ring on its tab label. These plugin landings do not arm the list's destructive keys.

Search changes keep the Input focused. A submit carries `isSubmit` on the query action and uses `landView` to focus the marked filtered row. With no matches, it lands on `find` after the safe tab label. The search button shows `rabe.query` independently of the Input's draft. This keeps the filter visible after Enter and reopening. An empty submitted query clears the filter. These landings also leave the list's destructive keys disarmed.

A sent message moves the ring from the agent's message Input back to its `m: message` control after delivery when that same agent detail and message field still own focus. The message press leaves `ringOn` intact while delivery is pending; the serialized landing checks ownership when it runs, so navigation during delivery keeps its focus.

- **Focus follows the person.** A `ui.focus` hook on the pane stores the item id of the `row:` element the ring lands on in `rabe.selected`, so the detail beside the list, the summary line, the marker and `x`/`g` follow the focus without Enter. Enter presses the focused row: it opens the item (from the Cost and Timeline tabs too, in the Items tab). A click presses a row too, on the terminal in the fullscreen layout, but moves no focus ring. So the ring and the selection can part: focus A, click B, and B is selected while the ring stays on A. The pane keeps the ring's element apart from the selection (`ringOn`: where its `ui.focus` hook last saw the ring land, unknown after a reset). On the Items list a press on the ring's row or on the selected row opens it, and a press on another live row only selects it (`selectsOnPress`). Enter presses the ring's row, so it always opens: focus A, click B, Enter opens A. Only a pointer presses a row away from the ring, so a click selects first and opens on the second click: click B, click B opens B. A click on the focused row opens it at once. The press is the person's choice of that row, so it arms `x` and `g` for it (see Arming).
- **Arrows and press landings.** Where all rows fit, ↑ and ↓ move the focus row by row (the engine does it, and wraps). In a pane taller than its body the engine scrolls instead and leaves the focus. A `ui.scroll` hook carries row arrows (no `pointer`, nonzero `|by|` smaller than the body height) through `sequence.ts`, then moves the focus by the summed `by` with `$.ui.focus`; the wheel and page scrolls pass. If a combined arrow reaches a list boundary, Rabe moves to the last valid row and passes only the remaining scroll through `offset`, since `by` is read-only. At either saturated viewport end, it passes the original offset to avoid reversing direction, which can overscroll by the rows Rabe consumed near that end. A press reserves its place in that same sequence before `next(e)`, then runs a view-changing action and its focus landings there. Person-originated focus moves that reach Rabe's `ui.focus` hook join the sequence when they move away from the ring's current key. In short panes the engine may move focus without a `ui.scroll` event, and the behavior after a view change is not fully verified live (see feasibility). Stop, delete, copy and message effects release the reservation before they wait on an external API; a message's final landing joins the sequence when it is ready. The pane then scrolls to show the landing. The rows are the `row:` Presses of the pane's drawing in the held document order (`rowKeys` of `hold`, without the `gone` slots), and the step is `stepRow`: from no row, ↓ goes to the first row; past the first or the last row the hook passes the scroll on, so ↑ shows the tab row and ↓ the controls. The hook draws the pane's view again from state to know the rows; their keys do not depend on the width, since the split's detail has no Buttons. Group headers are not arrow stops; Tab reaches them.
- **A change of the view moves the ring.** The engine keeps the ring on an index, and a new view (another tab, the open item, the search, a fold) draws other elements there: Enter on the first Cost row, then a click on `1: Items`, pressed `[ x: stop ]`. So `act` in `pane.tsx` moves the ring after each such change with `$.ui.focus`, key by key, as `landing(action, open)` in `view.ts` names them: first the active tab's Button, which is always drawn and never moves, then the element the change leads to: `b: back` of the item opened, the row of the item gone back from, the group header folded, the Timeline's `w` control after it widened the window. A key the new view does not draw leaves the ring on the tab. Search edits keep the ring in its Input. Enter returns it to the marked filtered row. Two calls also move the ring when it already sat on the second key at another index. While the pane does not hold the keys the calls are refused, and Enter goes to the prompt. Each such change also disarms the pane until a call lands (see Arming).
- **Presses run in a hook.** Rabe's own `$.ui.focus` from a Button's or Input's closure reaches none of Rabe's hooks (see feasibility), so the pane's `ui.focus` hook never saw a landing and every press that changed the view left the stops dim. So a closure only hands its action to the event it runs for, and the pane's `ui.press` and `ui.input` hooks (`carry`) run it beneath them and then carry it out with their own `$` through `act`, awaited, so a test's press settles with it. Events can be in flight at once (a plugin beneath may hold one open), so there is no shared slot: each event's hook adds its own slot, keyed by surface and element (`slotOf`), to a module map (`waiting`) before `next(e)`, and the closure, which the engine runs with the event's surface and element, fills the oldest empty slot of its element (`leave`). An event thus carries out only an action of its own element, and each action runs once. Two events on one element in flight at once may swap their actions, which are that element's either way. A focus sequence reservation is made before `next(e)`, so a row arrow cannot overtake a press whose closure is still running; a slow plugin beneath Rabe that holds a press open delays later presses and arrow moves. Only view changes and focus moves hold the reservation; external stop, delete and message calls run after it is released. If a press or Input fails after `next` ran because the drawing's handler is no longer held, its catch returns the event's harmless result and drops the action. The failed event does not reset arming, so the next key still works. Other failures pass through.
- **Back.** `b` in a detail goes back to the list, selects the item that was open and focuses its row (see above), since the ring would stay where `b` was. It selects the open item, not `rabe.selected`: in a workflow's detail the focus may have moved onto one of its agent rows, and `b` goes back to the run.
- **Keys.** On the list: ↑↓ move, Enter opens, `x` stop, `g` stop the group, `r` remove the selected row once it ended, `a` remove every ended row the search shows, `s` search; the hint names `x`, `g`, `r` and `a` only while they act. `g` stops the rows of the group the selected row is drawn in, as the search shows them: a held row that changed status stops with the group it stands in, not with the group of its status. When the selected row is a workflow or a workflow agent, `g` is `g: stop run` on that run instead, and `x` is dim: Claude Code stops a workflow only as a whole. Below the split the label of `s` keeps only the letter while the query is empty; `x: stop` and `g: stop group` keep their word. The hint under every tab names what works there (`↑↓ move · enter open · x stop · esc close`; on the Effects tab Enter on an `ssh -L` line copies it). In a detail: `b` back, `c` copy the command, prompt, agent id or resume command, `f` open the forwarder of a Codex job, `d` delete a cron job, `m` message an agent, `x` stop, `g` stop a workflow run. A workflow agent (`isWorkflowAgent`: its `parentId` is a `workflow:` item, or it has `workflowIndex` or `workflowPhase`) has no stop or message action and no message field, since Claude Code can stop only the whole run and cannot message a workflow agent: its detail offers `g: stop run` on the parent run when that run can be stopped, and the list leaves it out of `x` and of a group stop. Dim controls keep their own hotkeys with `NONE`. Other letters still reach the prompt because the mod API has no key hook (see feasibility). A letter also reaches the prompt in a view without that control.

The pane catches these letters while it holds the keys outside input fields:

| View | Letters caught outside input fields |
|------|-------------------------------------|
| Items list | `x g r a`; `s` where search is available |
| Agent detail | `b c x`; `m` on surfaces that support input fields |
| Workflow agent detail | `b c`; `g` when the parent run is known; no `x` or `m` |
| Workflow detail | `b g` |
| Shell or monitor detail | `b x`; `c` when a command is known |
| Codex detail | `b x`; `c` when a thread id is known; `f` when a forwarder is known |
| Cron job detail | `b c d` |
| Scheduled wakeup detail | `b c`; no `d` |
| Cost | `c` when the current session id is known |
| Effects | `c` on the first port's SSH row while that port exists |
| Timeline | `w` when `timelineHours` is greater than zero; `c` when the previous session id is known |

A focused input field takes every key.
