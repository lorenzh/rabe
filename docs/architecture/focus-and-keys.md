# Focus and keys

### The pane

`/rabe` is registered `immediate`, so it runs at once while Claude works instead of waiting for the turn. It opens the pane `rabe` with `closeOnEscape`, so Esc closes it; without it Esc only hands the keys back and the pane stays. The command requests focus after 50 ms through the [interaction model](interaction.md). If the command still occupies the prompt, the model retries after a new drawing. It stops when the pane has the keys, the pane is closed, or 40 requests have run. A resize that moves a focused pane between dock and inline requests focus after 500 ms. The model holds the last placement and keyboard ownership per surface. Until the pane holds the keys, the hint says "tab to select · esc close".

`paneView` draws the tab row as plain Buttons keyed `tab-<tab>` with the hotkeys `1` to `4`, which the engine draws as `1: ` before the label: `Items 7    Cost    Effects    Timeline` with `1-4 switch` at the right end at 90 columns and more, `Items 7  Cost  Effects  Timeline` below. No tab is ever cut off, since a lost tab would move every Button after it: where the labels do not fit, the gap shrinks to one, then the other tabs keep their first letter (`2: C`), and below that the tabs wrap onto more rows. The active tab is drawn full, the others dim, and a `━` line in orange under the active one, `1: ` included, marks it in the rule below the row (on one row only). Under the rule the toolbar holds the tab's controls and Inputs, then the body, then the hint. The desktop draws the same tree. Each value the pane keeps is a `$.state` key, so a hot reload keeps it:

| Key | What it holds |
|---|---|
| `rabe.tab` | The selected tab |
| `rabe.query` | The search text; matches title, kind, command, prompt, description and agent type |
| `rabe.folded` | The groups folded in the list |
| `rabe.selected` | The selected row's id (a click can select a row while the keyboard focus stays elsewhere; `ringOn` tracks the focus): set by a `ui.focus` that lands on a row, by a press that selects a row (a click, `selectsOnPress`), and by opening. An item id; only the Items tab writes it (#188) |
| `rabe.picked` | The selected row of each other tab, by tab name (an item id on Cost and Timeline, `file:<path>` or `ssh:<port>` on Effects). A focus that lands on a row there writes its own tab's entry, so a visit to Cost, Effects or Timeline never moves the Items selection. Absent: the tab's first row (#188) |
| `rabe.open` | The item whose full detail shows; `''` shows the list |
| `rabe.order` | The list order taken when the pane opened (`RabeOrder`, see [The held order](focus-order.md#the-held-order)) |
| `rabe.removed` | The ids of ended items the person removed this session (see [Removing ended items](views.md#removing-ended-items)) |
| `rabe.window` | The Timeline's window (`RabeWindow`: `base` hours from the option, the `hours` shown and their start `since`), set by `/rabe` and by `w`; absent, the pane takes the option's |

#### Focus and the arrow keys

Before a view changes, the pane focuses its safe tab in the old tree. After a tab switch, `landView` reads the new view and hands it to `landing`. The ring visits the safe tab label before the view changes. It then moves to the view's `autoFocus` control or marked row. An empty view leaves the ring on its tab label. These plugin landings do not arm the list's destructive keys.

Search changes keep the Input focused. A submit carries `isSubmit` on the query action and uses `landView` to focus the marked filtered row. With no matches, it lands on `find` after the safe tab label. The search button shows `rabe.query` independently of the Input's draft. This keeps the filter visible after Enter and reopening. An empty submitted query clears the filter. These landings also leave the list's destructive keys disarmed.

A sent message moves the ring from the agent's message Input back to its `m: message` control after delivery when that same agent detail and message field still own focus. The message press leaves `ringOn` intact while delivery is pending; the serialized landing checks ownership when it runs, so navigation during delivery keeps its focus.

- **Focus follows the person.** A `ui.focus` hook on the pane stores the item id of the `row:` element the ring lands on in `rabe.selected`, so the detail beside the list, the summary line, the marker and `x`/`g` follow the focus without Enter. Enter presses the focused row: it opens the item (from the Cost and Timeline tabs too, in the Items tab). A click presses a row too, on the terminal in the fullscreen layout. The click selects the row and Rabe moves the ring onto it with `$.ui.focus` (`ringOnto` in `pane.tsx`, issue [#186](https://github.com/lorenzh/rabe/issues/186)), so `x`, `r`, `c` and the arrows continue from the clicked row, as from the keyboard. A click on a tab label still lands on the tab's target like the hotkeys `1` to `4`: `ui.press` does not tell a click from a hotkey, so the ring cannot follow only the click there (#186). Only a refused focus move leaves the ring and the selection apart: focus A, click B, the move is refused, B is selected while the ring stays on A, and the arming clears, so `x` is inert until the person moves the ring. The pane keeps the ring's element apart from the selection (`ringOn`: where its `ui.focus` hook last saw the ring land, unknown after a reset). On the Items list a press on the ring's row or on the selected row opens it, and a press on another live row only selects it (`selectsOnPress`). Enter presses the ring's row, which after a click is the clicked row (after a refused move it is still A). Only a pointer presses a row away from the ring, so a click selects first and opens on the second click: click B, click B opens B. A click on the focused row opens it at once. The press is the person's choice of that row, so it arms `x` and `g` for it (see [Arming](focus-order.md#arming)).
- **Arrows and press landings.** Where all rows fit, ↑ and ↓ move the focus row by row (the engine does it, and wraps). In a pane taller than its body the engine scrolls instead and leaves the focus. A `ui.scroll` hook carries row arrows (no `pointer`, nonzero `|by|` smaller than the body height) through `sequence.ts`, then moves the focus by the summed `by` with `$.ui.focus`; the wheel and page scrolls pass. If a combined arrow reaches a list boundary, Rabe moves to the last valid row and passes only the remaining scroll through `offset`, since `by` is read-only. At either saturated viewport end, it passes the original offset to avoid reversing direction, which can overscroll by the rows Rabe consumed near that end. A press reserves its place in that same sequence before `next(e)`, then runs a view-changing action and its focus landings there. Person-originated focus moves that reach Rabe's `ui.focus` hook join the sequence when they move away from the ring's current key. In all-fit panes the engine moves focus without `ui.scroll`. The interaction model carries a focus move behind a pending press into the new held order. Stop, delete, copy and message effects release the reservation before they wait on an external API; a message's final landing joins the sequence when it is ready. The pane then scrolls to show the landing. The rows are the `row:` Presses of the pane's drawing in the held document order (`rowKeys` of `hold`, without the `gone` slots), and the step is `stepRow`: from no row, ↓ goes to the first row; past the first or the last row the hook passes the scroll on, so ↑ shows the tab row and ↓ the controls. The hook draws the pane's view again from state to know the rows; their keys do not depend on the width, since the split's detail has no Buttons. Group headers are not arrow stops; Tab reaches them.
- **A change of the view moves the ring.** The engine keeps the ring on an index, and a new view (another tab, the open item, the search, a fold) draws other elements there: Enter on the first Cost row, then a click on `1: Items`, pressed `[ x: stop ]`. So `act` in `pane.tsx` moves the ring onto a safe tab before each such change and onto its target afterward with `$.ui.focus`, key by key, as `landing(action, open)` in `view.ts` names them: first the active tab's Button, which is always drawn and never moves, then the element the change leads to: `b: back` of the item opened, the row of the item gone back from, the group header folded, the Timeline's `w` control after it widened the window. A key the new view does not draw leaves the ring on the tab. Search edits keep the ring in its Input. Enter moves it to the first filtered row (`rowKeys` in `landing`). The `ui.close` hook with origin `person` refuses a close while the ring is on `search` and the query is not empty (`holdsClose`), so the pane and the filter stay (#187). The engine releases the pane's keyboard before it raises the close (`ui.focus` is then refused with `that site does not hold the keyboard`), so the hook cannot land the ring: it only drops the ring state (`unfocused`), and the keys go to the prompt until the person presses `ctrl+x tab`. Whether a mod can keep the keyboard through a person's close is not shown. The ring state lives in a module value, so after a reload of the hooks the marker and this guard return with the first focus event. The Input takes no style, so `isOnSearch` in the selection prefixes its label with `▸`. The `k` button (`clear-search`, last in the list's controls, dim without a query) submits an empty query. The safe tab keeps its index across the view change. A second call lands on the new target. Before that call, a landing that changed the view waits, once its own tab step put the ring on the tab (`landOn`; a retried tab counts, a refused one ends the landing), for a drawing of the new view (`onScreen` in `pane.tsx`, `screens` in `sequence.ts`). The engine finds a key in the tree on screen, so a key that the old view draws at another index takes that index, and the new view keeps the ring there: on a control (issue [#174](https://github.com/lorenzh/rabe/issues/174), see item 9 in [feasibility](../feasibility/ui.md#buttons-focus-and-the-mouse)). The wait asks for a drawing (`$.ui.invalidate`), waits for a `ui.render` that began after the ask, and then waits 100 ms (`SHOW_MS`). This is timing, not a barrier: no event says when a drawing is on screen, and Rabe cannot check where the ring went, because the engine reports a landing on the asked key even when the ring keeps the old index. When no such drawing comes within 300 ms (`DRAW_MS`), a `$.clock.sleep` is refused, the next press, Input event or arrow comes, the person moves the focus, or the pane closes, the wait gives up and Rabe does not move the ring to the target. The press then releases its place in the sequence, and a key that ended the wait runs as usual from where the ring is. The wait is 100 ms after the drawing, so it usually takes about 100 to 130 ms and at most about 400 ms when the drawing comes near the 300 ms fallback. Tab switches, a fold and a submitted search wait this way (`waitsForView` in `view.ts`): a fold of the selected agent's group drops its message Input above the headers. A live search edit does not wait. It focuses the search Input at once, as before, because during a wait a typed key or Enter would reach whatever control took the Input's index. The list keeps the slots of `c`, `m` and `d` (dim, `NONE`) when nothing is selected, so a search with no match leaves the Input at the same index (13 at 140 columns; it was 10, a stop that the shorter tree lacked past the ring's index, and the engine dropped the ring from the pane and the next keys went to the prompt, [#180](https://github.com/lorenzh/rabe/issues/180)). Opening an item and going back do not wait: in the live check, `Enter b Down Down` reached the next rows on main. Nor do the Timeline's window and a sent message, which keep their target's place. `landOn` in `view.ts` holds the order of the calls, and `view.test.ts` checks it against a stand-in of the engine's ring. `sequence.test.ts` checks the wait with a stand-in clock. While the pane does not hold the keys the calls are refused, and Enter goes to the prompt. Each such change also disarms the pane until a call lands (see [Arming](focus-order.md#arming)).
- **Presses run in a hook.** Rabe's own `$.ui.focus` from a Button's or Input's closure reaches none of Rabe's hooks (see [feasibility](../feasibility.md)), so the pane's `ui.focus` hook never saw a landing and every press that changed the view left the stops dim. Fixed tab actions run directly in the press hook, so they need no drawing handler. For other controls, a closure only hands its action to the event it runs for, and the pane's `ui.press` and `ui.input` hooks (`carry`) run it beneath them and then carry it out with their own `$` through `act`, awaited, so a test's press settles with it. Events can be in flight at once (a plugin beneath may hold one open), so there is no shared slot: each event's hook adds its own slot, keyed by surface and element (`slotOf`), to a module map (`waiting`) before `next(e)`, and the closure, which the engine runs with the event's surface and element, fills the oldest empty slot of its element (`leave`). An event thus carries out only an action of its own element, and each action runs once. Two events on one element in flight at once may swap their actions, which are that element's either way. A focus sequence reservation is made before `next(e)`, so a row arrow cannot overtake a press whose closure is still running; a slow plugin beneath Rabe that holds a press open delays later presses and arrow moves. Only view changes and focus moves hold the reservation; external stop, delete and message calls run after it is released. If a press or Input fails after `next` ran because the drawing's handler is no longer held (the engine answers `no handler is held under handle`), its catch returns the event's harmless result and drops the action. The search field is the exception: the engine releases a drawing's handlers when Rabe draws the pane again, so a redraw between a key and its closure (the one-second tick, or the drawings a query that brings rows back starts) rejected that key's change, and the filter stayed one key behind the field. In the live check a Backspace from `z` to an empty field left the list filtered by `z`, and the next `s` drew the field with `z` again. The event carries the field's whole text (`e.value`), so the `ui.input` hook catches that rejection for the `search` Input and carries out the query the field's own action builds from it (`queryOf` in `views/items.ts`); a press, and any other Input, is still dropped, since its action follows a drawing that is gone. A submit in an agent's message field (`message:<id>`) is the second exception (#218): the hook takes the id from the key and the text from `e.value`, checks again that the agent is live, not a workflow agent and the text is not empty (`lostMessage`), and puts the `message` action into this event's own slot, so it is sent once through `act`; a submit whose closure already ran (slot filled) is not sent again, and identical text is not deduplicated over time. A `change` event never sends. A refusal shows `Message not sent` (with the engine's reason when the send ran), an exception after the send started shows `Delivery unknown`, and the send is never repeated. A toast holds no message text. The failed event does not reset arming, so the next key still works. Other failures pass through.
- **Back.** `b` in a detail goes back to the list, selects the item that was open and focuses its row (see above), since the ring would stay where `b` was. It selects the open item, not `rabe.selected`: in a workflow's detail the focus may have moved onto one of its agent rows, and `b` goes back to the run.
- **Keys.** On the list: ↑↓ move, Enter opens, `x` stop, `g` stop the group, `r` remove the selected row once it ended, `a` remove every ended row the search shows, `s` search; the hint names `x`, `g`, `r` and `a` only while they act. `g` stops the rows of the group the selected row is drawn in, as the search shows them: a held row that changed status stops with the group it stands in, not with the group of its status. When the selected row is a workflow or a workflow agent, `g` is `g: stop run` on that run instead, and `x` is dim: Claude Code stops a workflow only as a whole. Below the split the label of `s` keeps only the letter while the query is empty; `x: stop` and `g: stop group` keep their word. The hint under every tab names what works there (`↑↓ move · enter open · x stop · esc close`; on the Effects tab Enter on an `ssh -L` line copies it). In a detail: `b` back, `c` copy the command, prompt, agent id or resume command, `f` open the forwarder of a Codex job, `d` delete a cron job, `m` message an agent, `x` stop, `g` stop a workflow run. A workflow agent (`isWorkflowAgent`: its `parentId` is a `workflow:` item, or it has `workflowIndex` or `workflowPhase`) has no stop or message action and no message field, since Claude Code can stop only the whole run and cannot message a workflow agent: its detail offers `g: stop run` on the parent run when that run can be stopped, and the list leaves it out of `x` and of a group stop. Dim controls keep their own hotkeys with `NONE`. Other letters still reach the prompt because the mod API has no key hook (see [feasibility](../feasibility.md)). A letter also reaches the prompt in a view without that control.

The pane catches these letters while it holds the keys outside input fields:

| View | Letters caught outside input fields |
|------|-------------------------------------|
| Items list | `x g r a`; `s k` where search is available (`k` stays caught and dim while there is no filter); at 90 columns or more, the selected detail's `c m d` controls |
| Agent detail | `b c x`; `m` on surfaces that support input fields |
| Workflow agent detail | `b c`; `g` when the parent run is known; no `x` or `m` |
| Workflow detail | `b g` |
| Shell or monitor detail | `b x`; `c` when a command is known |
| Codex detail | `b x`; `c` when a thread id is known; `f` when a forwarder is known |
| Cron job detail | `b c d` |
| Scheduled wakeup detail | `b c`; no `d` |
| Cost | `c` when the current session id is known |
| Effects | `c` on the first port's SSH row while that port exists |
| Timeline | `w` when `timelineHours` is greater than zero; `c` when the previous session id is known |

A focused input field takes every key.

## Selection across tabs, remove and reopen (#188)

The Items tab keeps `rabe.selected`; every other tab keeps its own entry in `rabe.picked`. `look` hands the views the active tab's value as `selection.selected`, and the `ui.focus` hook writes to the active tab's key. `r` (and `a`) moves the selection to the next row of the list as drawn, or to the previous one at the end, when the selected row is among the removed ones, and disarms the pane, so `x` acts on the neighbour only after the person moves the ring (see [Arming](focus-order.md#arming)). When the pane reopens, `refocus` calls `restore`, which lands the ring on the stored tab and its selected row (the keys of `landing`). It runs only while the pane holds the keys, and the open counts as done only after every call landed, so a retry while the prompt still held the keyboard is not lost. A landing the host refused (such as an abandoned move) is asked again every 50 ms, at most 40 times. A retry goes on while the pane reports no focus and opens it again: the open's own retries (`opening`) stop once the pane first held the keys, so without it a pane that lost the keys after a refused landing stayed off its row. The calls come from a `$.clock.after` callback, which runs none of Rabe's focus hooks (item 14 in [feasibility](../feasibility/ui.md#buttons-focus-and-the-mouse)), so the engine's answer is the verdict, not `landedOn`. Each call the engine did not refuse feeds `restored`, which records the key as `ringOn` without arming, so rows that shift above the ring after the reopen ask a regain and hold Enter back. The test kit refuses Rabe's own `$.ui.focus`, so `landOn` answering whether every key landed and the `restored` event are unit-tested, and the landing is covered by the live check `reopen`.
