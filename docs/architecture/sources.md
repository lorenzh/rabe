# Sources

## The source contract

Polled sources take a `Pollers` list from `hooks/loop.ts`. Event-only sources take `on` and register their hooks directly.

A source is a function in `hooks/sources/<kind>.ts` that registers its own hooks with `on`. Its hooks call `next(e)` unless they answer on purpose, and they never throw. To add a source, import it in `hooks/sources/index.ts` and call it in `sources(on, file, pollers)`:

```ts
export function sources(on: On, file: string, pollers: Pollers): void {
  agents(on, file, pollers)
  shells(on, pollers)
}
```

The polled sources add bound callbacks to `pollers` from their matched start hooks. Each callback receives the current staged items and returns `Change | undefined`. Multi-change polls use a local `Poll` and return `changeOf(poll)`. Event writers take no poll argument. The [shared loop](../architecture.md#shared-poll-loop) publishes them together. Event hooks still write immediately.

A source owns the items of its kind. It uses `itemId(kind, nativeId)` for ids, so another source can set `parentId` without asking it. Test a source through the engine: raise its events in a test, and watch `rabe.items` with a test hook on `state.set`.

### Starting work: `session.start` with a matcher

`pane.tsx` owns the plain `session.start` hook. Each source gives its own start hook a matcher (see [the engine's rule for `$`](state.md#the-engines-rule-for-)): the agents source uses `{ cwd: /^/ }`, and the Codex and worktrees sources use `{ isInteractive: true }`, since only a person at the prompt sees the band and the pane.

### Stopping an item

The pane stops agents, shells, monitors and workflows itself: it calls `TaskStop` through `$.tool.call` (see [Actions under The pane](focus-and-keys.md#the-pane)). A Codex job has no task id, so it stops through a command instead. `/rabe-stop codex:<job id>` is registered by the Codex source (with `immediate: true`, so it also runs during a turn). Its command hook matches `{ command: 'rabe-stop' }` and answers every call with `{ text }`. Arguments starting with `codex:` use the existing cancellation path. Empty arguments or arguments without that prefix return fixed usage text without stopping work or repeating the input. The hint shows `codex:<job id>`. Use the Codex job id shown in Rabe, not the thread id. To stop other items, use `x` in the pane. The answer is a transcript line that Claude reads, so it names the job by its job id (`Stopped codex task-1`), never by its title. The person can type `/rabe-stop codex:<job id>`. The pane's `x: stop` on a Codex job runs the same command with `$.command.run({ command: 'rabe-stop', args: <item id> })` and shows its answer as a toast, so the cancel stays in the Codex source. A companion refusal returns fixed text to keep stderr out of Claude’s transcript. The source keeps the first error line in the item’s session-only `detail.stopError`. The pane reads that field for its refusal toast. A successful cancel clears it.


## The sources

### Claude subagents: `hooks/sources/agents.ts`

Pure metadata, transcript, turn and item helpers live in [`agent-items.ts`](agent-items.md). Hooks and `$` helpers stay in `agents.ts`.

One `agent` item per subagent, id `agent:<agentId>`. It covers agents the model starts, agents of workflows and teammates.

The agent-list poll stores an API-provided `name` and uses it for the title. Message toasts use the agent id. Without a name, the title uses the task description or agent type. Turn tool paths stay whole in `rabe.turns`; the detail shows project-relative paths when it can, with a middle ellipsis for long paths.

| Hook | What it does |
|---|---|
| `agent.spawn` | After `next(e)` gives the `agentId`, adds a running item: title from the description (else the type), type, model, the prompt (`detail.prompt`, cut to 600 characters), `startedAt`. Keeps teammate identity from `isTeammate` or the result’s `teammateId`. A workflow agent gets `parentId` `workflow:<runId>` and `workflowIndex`; an agent started by another agent gets `agent:<parentAgentId>`. A refused spawn adds nothing. |
| `classic.SubagentStart` | Fires inside the spawn, before `agent.spawn` adds the item, so it adds a running item (title the agent type) when none exists; the spawn then merges its fields in. Sets `transcriptPath` (`<session>/subagents/agent-<id>.jsonl`, built from the hook's `transcript_path`); `agent.spawn` moves a workflow agent's path into `<session>/subagents/workflows/<run-id>/`. It also sets `cwd`. It never sets `worktreePath`: a `cwd` that is not the session's may be the agent's worktree or a plain subfolder, and only the meta file or git tells them apart. |
| `turn.step` with `agentId` | After the response, adds its tokens (`input` is uncached input plus cache writes plus cache reads, `cached` is the cache reads inside `input`, the same as Codex counts them) and its price (`claudeUsd` of the usage's model, see [the cost estimate](prices.md#the-cost-estimate)) to `costUsd`, sets `model`, `toolCount`, `lastTool` and `lastToolAt`, puts the item back to running, and adds a turn to `rabe.turns`. Steps of loops Rabe has no item for (forks for compaction or memory) are ignored. |
| `tool.call` for `Edit` and `Write` | After the call, when it changed the file (`changedFile`: a result, no error, and not `staged` for review), adds `{ path, at, via }` to the agent's `detail.edits`, or without `agentId` to the main session's `rabe.edits`; the path from the result's `filePath`. A refused, failed or staged edit adds nothing. The Effects tab reads these, not the turns: a turn lists the calls the model asks for, which may be refused. |
| `tool.call` for `Bash` in a subagent, a Codex companion call | `companionCall(command)` (in `forwarders.ts`) finds a command line that runs the Codex plugin's `codex-companion.mjs` with `task`, `review` or `adversarial-review`. Before `next(e)` the agent's `detail.codexCalls` gains `{ at, command, text }` (the line cut to 600 characters, the newest 10 calls kept). After the call: a call moved to the background (`backgroundTaskId`, also a timeout) still runs and gets nothing; a refused one gets `endedAt`; one that ran, also with an error, gets `endedAt` and what `companionOutput` reads in its stdout and stderr: `jobId` from `started in the background as <id>.`, `threadId` from the progress line `[codex] Thread ready (<id>).`. The main session's calls are not kept (see Forwarders). |
| `tool.call` for `Bash` | Before `next(e)`, `beforeBash` stats the absolute candidates of `shellWrites(command, cwd, HOME)` (at most 20; `look` gives up after 1 s). After a call that ran to its end (`ranBash`: a result, no error, not interrupted, not in the background), `afterBash` stats them again and adds each path `changed(before, after)` names (after a failed stat, `isMissing` lists the parent folder: a listing without the name, or a parent that is missing by the same rule, makes the path missing; a listing that fails or still has the name, in any letter case or Unicode form (NFC), leaves it unknown; one listing per folder per look, inside the 1 s limit; error text is never read), `via: 'shell'`, to the agent or the main session as above. When parsing without `cwd` leaves a relative candidate, the hook reads the folder. For the main session, `cwd` comes from `$.session.cwd()` at that call. For an agent, it comes from the item’s `detail.cwd`. An unknown folder leaves relative paths out (see [feasibility](../feasibility.md)). |
| `turn.complete` with `agentId` | Sets a known teammate idle unless the agent list reports `completed`, `failed` or `killed`. Ends a plain subagent: `answer` is done, `aborted` is stopped, `refusal` and `error` are failed. Reads the meta file once more from the workflow directory for a workflow agent, else next to its transcript. |
| `session.start` | Binds the agent poll for the shared loop. The loop runs it once at session start. |

After a completed Bash call, `afterBash` also reads absolute paths from the result's `bashEditDiff.changedFiles`. It merges them with disk-confirmed paths once per call. A matching `files` entry can mark a deletion. Rabe stores no hunks and writes no state for an empty change list.

Missing or malformed fields give no paths. A diff marked `shared`, `skipped` or `unavailable` gives no paths. A failed or timed-out disk check does not discard usable host paths. Script coverage needs `auto` mode or `bashEditDiffEnabled` (see [file source limits](../feasibility/files.md)).

The poll reads `$.agent.list()`. It adds agents Rabe has no item for (started before Rabe loaded, or dropped by the cap). An ended one never gets a new recency: it takes `pastEnd`, the oldest end held, and is not added at all once 200 ended items are held, since the cap would drop it. So an unchanged list causes no write, however many ended agents it holds, and agents Rabe did not watch never push out the ones it did. The poll also ends items the list reports as `completed`, `failed` or `killed`. An agent can resume under the same id: when the list shows an ended item's agent as `pending`, `running` or `waiting`, the poll sets it running again and clears `endedAt`, and one the cap dropped is added back as running. An idle teammate stays alive without `endedAt`. The list’s `teammateId` or stored `detail.isTeammate` proves teammate identity. A plain subagent reporting `idle` keeps its held status; an unwatched one starts as running. Then it reads the meta file of each running agent and idle teammate and copies `cwd`, `worktreePath`, `worktreeBranch` and `workflowPhase`. A workflow agent whose phase is not known is also checked while its run declares phases, including after it ends, so a short agent appears under its declared phase when that metadata arrives later. A workflow with no declared phases is not polled for metadata after its agents end. An agent with neither `cwd` nor `worktreePath`, or with only a `cwd` that is not the session's, shows its tree as `n/a`, not as the main tree. The meta file sits next to an ordinary agent's transcript (`agent-<id>.meta.json`); for every workflow agent it is in the run's `transcriptDir`, or in the folder derived from the script path. The file appears about 1.5 seconds after the start and changes later. The poll caches its size and modification time. It reads the file again only after these change.

Workflow agents are not in `$.agent.list()`: only `turn.complete` ends them.

### Workflows: `hooks/sources/workflows.ts`

One `workflow` item per run, id `workflow:<runId>`.

| Hook | What it does |
|---|---|
| `tool.call` for `Workflow` | After the call, takes `runId`, `taskId`, `workflowName`, `scriptPath` and `transcriptDir` from the result and adds a running item. A resumed run keeps its `runId` and runs again under the same item. Then it checks the script path against this session’s `workflows/scripts/` folder under the Claude projects folder. It checks the resolved file against the resolved folder before reading. A rejected path leaves phases unknown. It reads an accepted script for the phase names in its `meta.phases` block. It stores these in `phases` in order. Names come from strings or an object’s `title`. A bracket inside a phase string (`'Review [fast]'`) does not end the list. A remote run has no `runId` and gets no item. |
| `prompt.submit` with origin `task-notification` | Reads `<task-id>` and `<status>` of each `<task-notification>` in the text (with `parseNotifications`; one prompt can carry several). When a task id is a run's `taskId`, it ends the run: `completed` is done, `failed` is failed, `killed` is stopped. |

The run's agents come from `agents.ts`; they point to the run with `parentId` and carry their phase in `workflowPhase`. A view gets a run's tokens by adding up its agents.

### Codex jobs: `hooks/sources/codex.ts`

[`codex-data.ts`](codex-data.md) holds pure job and rollout parsing (`parseRollout`, `advanceRollout`) and item construction (`codexItem`). `codex.ts` keeps polling, file reads, stat confirmation and cancellation.

Tracks the jobs that the Codex plugin (`codex@openai-codex`) starts for this session. Data sources and their limits are in [Codex job feasibility](../feasibility/background-work.md#codex-jobs).

- **Poll.** `session.start` (interactive only) binds the Codex poll for the shared loop. The loop skips ticks while a pass runs. Each poll lists the plugin's state folders, skips each whose `state.json` was not changed since the session started (`$.session.usage().startedAt`), and reads the rest. It keeps the jobs whose `sessionId` is this session's (`$.session.id()`), and checks that again in the job file, because `state.json` can hold a bare status patch without it. An ended job is read again only while its cursor has a backlog. For a finished job Rabe holds no item for, the poll first asks `commit` whether the item would change the list; when the cap would drop it again (it ended before every ended item held, so the cap dropped it before), its session file is not read and nothing is written. The other polls add only work in flight (`background_tasks`, `session_crons`), which the cap never drops.
- **Item.** `codexItem(job, session)` builds the item. Title: the first line of the job's `summary` (the prompt's start). Status: `queued` and `running` are running; `completed`, `failed` and `cancelled` end the item as `done`, `failed` and `stopped`, with `endedAt` from `completedAt`. Undefined fields are left out, so a merge never erases a known value.
- **Session file.** The rollout path is found once by `threadId` near the start day. It stays in `detail.sessionPath`. A session cursor records size, modification time, inode and byte offset. Unchanged files cause no content read. New bytes arrive through `tail -c +N`. Large files catch up over several polls. `isSessionPartial` marks a backlog or a skipped oversized record. A finished job without a file gets `isSessionMissing`. Its model and effort then come from the job's request. A gone or unreadable file clears its cost estimate. Each job failure leaves the other jobs running. See [incremental file reads](reading.md).
- **`parseRollout(text, home, since, until)`.** Pure. `since` is the job's start (`startedAt`, else `createdAt`): a job that resumed a thread (`task --resume-last`) shares the session file with the jobs before it, so a record whose `timestamp` is before `since` gives nothing but the model, effort and sandbox of its `turn_context` and, for a `token_count`, the thread's total at the job's start. `until` is a finished job's `completedAt` (none while it runs or without the field): a record after it belongs to a later job on the thread and gives nothing, not even its `turn_context`. A record without a time counts as the job's. Reads model, effort and sandbox (`turn_context`), the prompt (first `UserMessage`), tokens (last `token_count` total, less the thread's total at the job's start; after earlier records with no total among them, unknown), `requests` (each `token_count` whose total changed gives its `last_token_usage` with the model of the last `turn_context` before it; a count missing leaves the request without a model, so without a price; a record without counts, `info: null` for rate limits only, adds none and leaves the last total in place), and the steps: assistant messages, reasoning summaries when present, finished commands (`CommandExecution`, with exit code and output line count), and a running command (a `custom_tool_call` that has no output yet). Steps keep the last 50, each text cut at 300 characters. `edits` (the newest 100, left out when none) are the paths of each completed `FileChange` (`via: 'codex'` with its `add`, `update` or `delete`) `checks` (the newest 100) are the absolute write candidates `shellWrites` finds in each `CommandExecution` with exit code 0 and a `started_at_ms`, against its `cwd`, with the command's run as `from` and `to`; a command with over 20 is skipped. `confirmed` stats each check when the session is read and adds a file whose mtime lies in the run (plus 2 s) to `edits`, `via: 'shell'`, sorted by time. A poll stats each path once for all its jobs (`Looks`), and all its checks share one 1 s deadline from the first check: a path whose stat has not come back by then (a stalled network mount) is left out, and the `FileChange` edits are still written. The `cwd` URL is decoded per path segment, so `%23` and `%3F` become `#` and `?`. Lines that do not parse (a line still being written) are skipped.
- **Cost.** `advanceRollout` keeps parser settings and totals between chunks. Each chunk prices only its new requests. Session state keeps their sum. A chunk without requests keeps the sum. An unpriced request makes it unknown. A partial rollout has no estimate until its backlog is consumed. A skipped oversized record keeps the estimate unknown. An unchanged file keeps the item's cost.
- **Forwarders.** After the jobs, each poll links jobs to the agents that started them (`linkForwarders` in `forwarders.ts`, one staged change only when a link changes). A job gets `parentId` `agent:<id>` only on proof: the agent's call named the job (`jobId`); or the job started (`startedAt`) at or after the call and, when the call returned, before its end, is of the call's kind (`task` is `rescue`, `review`, `adversarial-review`), and has the call's `threadId`, or, while the call names none, its title (the companion's summary of the prompt, without the `...` of a cut) is in the call's command line, compared without quotes, backslashes and extra spaces. Exactly one call may fit the job, and that call may fit no other job; else the job has no parent. Each poll decides every link again from the calls and jobs it holds, so a link the prompt made moves when the call returns a job id or thread of another job (the main session started a job with the same prompt, and it showed first), and goes while a second job fits. A forwarder that loses its job gets its row back. The views fold a pure forwarder into its job (see the Items tab).
- **Stop.** `/rabe-stop codex:<job id>` runs `node <plugin root>/scripts/codex-companion.mjs cancel <job id> --json --cwd <workspaceRoot>` with `CLAUDE_PLUGIN_DATA` set to the plugin's data folder. The plugin root is the `installPath` in `plugins/installed_plugins.json`. On success the item ends as `stopped`. Later polls skip it, so it keeps its cost only while its session file still has the `mtimeMs` the cost was read from (`sessionUpdatedAt`); a file that changed or is gone makes the cost unknown.

The codex detail fields are listed in the table above. `steps` holds `RabeCodexStep` values: `{ kind: 'message' | 'reasoning' | 'command', text, exitCode?, lines?, isRunning? }`.

The next three sources follow the work Claude Code runs as background tasks. Each writes items of its own kind only. The pure parsing lives in `hooks/tasks.ts` and `hooks/schedule.ts`, so views can use it too.

### Shells: `hooks/sources/shells.ts`

A shell title uses the normalized Bash description when present, else the normalized command, followed by the task id. The detail keeps the original command. An empty running shell says `No output yet`; a shell that ended says `No output`.


| Hook | What it does |
|---|---|
| `tool.call` `{ tool: 'Bash' }` | After `next(e)`: a result with `backgroundTaskId` adds `shell:<taskId>`, titled with the normalized description or command and task id. `outputPath` comes from the result text (`Output is being written to: …`). This covers `run_in_background`, Ctrl+B and a timed-out command. In a subagent, `parentId` is `agent:<agentId>`. A call without `run_in_background` that is still running after 2 s gets `shell:fg-<tool_use_id>` (no `taskId`, so no stop button), removed when the call returns; a call moved to the background leaves only its `shell:<taskId>`. A detached `codex exec -o <file> &` (`codexExec` in `hooks/codex-exec.ts`) keeps that row with `detail.resultPath`; the shells poll ends it as done when the file exists with a modification time not before `startedAt`. See [background work](../feasibility/background-work.md#foreground-bash-calls-and-direct-codex-exec). |
| `prompt.submit` `{ origin: { kind: 'task-notification' } }` | Each `<task-notification>` with a `<status>` ends its shell: `completed` is done, `failed` failed, `killed` stopped. The exit code comes from the summary (`failed with exit code 3`). It reads the output file once more first, so a shell that ended between two polls keeps its last lines. |
| `session.start` | Binds the output poll for the shared loop. It reads the output file of each running shell, keeps its lines in `rabe.lines` (as the monitors source does), guesses a port (`localhost:5173`, `port 4000`) and keeps the time it found it as `portAt`, and ends the shell at the last line `[exited with code N]` or `[killed]`. The poll keeps a byte cursor and reads only new output. Large files catch up over several polls. Their newest 200 lines still reach the detail. |
| `classic.Stop` | A running shell missing from `background_tasks` ends by its exit line, else as stopped. A shell a subagent started (`parentId` `agent:…`) is skipped: it may be missing from the main session's list while it runs, and the poll ends it from its file. A shell in `background_tasks` that Rabe never saw is added, without `startedAt`. Claude Code lists a Monitor tool task with type `shell` too, so a task id Rabe already has as `monitor:<id>` is skipped; a monitor started before Rabe loaded still shows as a shell. |

The same start hook adds a `ports` poll every 6 seconds, after the output poll. It checks only running shells with a validated output path and no port. `hooks/ports.ts` holds the pure parent-tree and listener parsers. The socket poll checks Linux with `uname`, gets file holders with `fuser`, and shares one `ps` and `ss` snapshot. All owners of a listener must be in that task’s tree. A found port and `portAt` use the shared staged commit. Replay skips shells that ended or already gained a port. Calls never overlap with another shared poll. See [background work](../feasibility/background-work.md#background-shells) for source limits.

A subagent's shells and monitors get no end notification in the main session: it goes only to the subagent (see [feasibility](../feasibility.md)). Their output files are in the main session's `tasks` folder, so the poll ends them from the file's last line, `[exited with code N]` or `[killed]`, as it does every shell.

### Monitors: `hooks/sources/monitors.ts`

The same four hooks for the Monitor tool, with the same `classic.Stop` rule for a subagent's monitor. The Monitor result has no file path, so `outputPath` is the sibling of a task output file Rabe already knows (`taskOutput`, tried again on each poll), or the `<output-file>` of the end notification. A subagent's monitor has no end notification in the main session, so it ends from its file once Rabe knows any task output path.

The end notification is handled only for task ids Rabe has as `monitor:<id>`: a shell's notification also carries an `<output-file>`, and reading it would file shell lines under a monitor id.

Monitor lines are kept apart from the item, in the `$.state` key `rabe.lines`: `Record<itemId, { seen, lines: { at, text }[], cursor? }>`. `seen` counts the lines read from the file; `lines` holds the newest 200, each with the time the poll first read it ("received"). A last line read while it was still being written (`hel`, then `hello`) is updated in place and keeps its time. The poll and the end notification both read the file, so the last lines are kept even when the notification comes first. Notification `<event>` lines are not used: they come late and in batches. The lines of an item dropped from `rabe.items` go with it, in the write that drops it (see [the write loop](state.md#the-write-loop)), as its turns do.

### Cron jobs and loops: `hooks/sources/crons.ts`

| Hook | What it does |
|---|---|
| `tool.call` `{ tool: 'CronCreate' }` | Adds `cron:<id>` with `schedule`, `humanSchedule` and `prompt`. |
| `tool.call` `{ tool: 'CronDelete' }` | Ends the job as stopped and sets `detail.isDeleted` on a successful deletion. The list and detail label it deleted. |
| `tool.call` `{ tool: 'ScheduleWakeup' }` | Ends the running wakeup as done and adds `cron:wakeup-<scheduledFor>` with `scheduledFor` and no schedule. `stop: true` ends running wakeups as stopped. The `<<autonomous-loop-dynamic>>` prompt shows as "autonomous loop". |
| `prompt.submit` `{ origin: { kind: 'scheduled-trigger' } }` | Ends a wakeup due by now (plus 90 s, since a wakeup can fire early) as done only on evidence that it fired: the fired text is its prompt (a `/loop` wakeup fires its input verbatim), or its prompt is a sentinel such as `<<autonomous-loop-dynamic>>` and the text names it (the expanded dynamic tick tells the model to re-arm with that sentinel). Any other text ends nothing, also the expanded tick of a recurring `<<autonomous-loop>>` cron job, which names no sentinel. A wakeup whose tick Rabe does not recognise stays running until the next `ScheduleWakeup` ends it as done, or `stop: true` as stopped; it ends late, never early. |
| `session.start` | Calls `CronList` and adds the jobs made before Rabe loaded. |
| `session.append` `{ door: 'prompt' }` | Keeps the main user row UUID in `rabe.cronTurn`. A new prompt invalidates a turn link. |
| `turn.step` `{ index: 0 }` | Reads confirmed fire/user pairs from the session transcript. Updates fire counts and times. Binds an exact observed prompt UUID to the main turn id. |
| `turn.complete` | Reads the pairs again. Records the end word only when the main turn id, prompt UUID and fire UUID still match. Ignores subagents. |
| `classic.Stop` | Syncs with `session_crons`: a job gone from the list ends as done (a one-time job fired, a job expired); a new one is added. Wakeups are not ended here, and a listed job whose prompt matches a running wakeup is not added twice. |

`crons.ts` keeps the pure `cronFires` parser beside the hooks. It counts unique fire/user pairs by exact task and fire ids. It hides ambiguous jobs and ignores sidechains and tool-result rows. Session start also restores fire counts for listed jobs. The main `classic.Stop` event supplies `transcript_path`, kept in `rabe.cronTranscript` only when changed. Subagent events cannot replace it. The reader accepts only absolute `.jsonl` paths. `grep -F` filters fire and scheduled user rows with a five-second timeout. The scan runs at session start for any listed cron and before the first model step only while a cron is running. At completion it runs for the turn that `rabe.cronTurn` links and once for a cron that ended during the turn and still lacks fire details. Deleted and ended crons therefore start no scans on unrelated later turns. A counter of replacing prompts, kept in module memory, is compared when completion builds its item write; a newer prompt cancels the end word, because a state re-read inside one dispatch shows the same moment. No matches supply empty fire data. Failed or truncated reads supply no new details. Ordinary prompts can be absent from the filtered text: the UUID in `rabe.cronTurn` must still match the fire user before a turn can bind. End words stay in item detail and describe the API turn end only. See [the confirmed fields and limits](../feasibility.md#cron-fire-identity-and-turn-end).

`schedule.ts` has `nextRun(expr, from)` and `nextRuns(expr, from, count)`: the next times a 5-field cron expression matches in local time, after `from`. It reads `*`, numbers, ranges, lists and steps; day of month and day of week match either one when both are set, as in cron. Minutes advance in real time, so a next run is never earlier than `from`, also in the hour that repeats when summer time ends (a job in that hour can show twice). A broken or impossible expression gives `undefined` (an empty list). Claude Code adds up to 10 % jitter to recurring jobs, which this does not show. The band's next run (`nextAt` in `lists.ts`) and the cron detail use `nextRuns` too.

`writes.ts` has `shellWrites(command, cwd, home)`: the files a shell command line may write or delete, each `{ path, isDeleted? }`, the last change to a path winning. They are candidates: the callers check them on disk, and `changed(before, after)` says from two looks whether a path was written, deleted or left alone. It never throws and runs in linear time. `lex` in `shell-words.ts` reads the words with bash quoting and drops comments and here-doc bodies; a word keeps whether it has an expansion, whether it can become more or fewer words, and whether its first character is literal, which decides if it can turn into an option. Command substitutions are skipped as a whole with their own quotes and nesting (64 levels at most), so nothing in them counts. `simple` takes the redirections out of a command and unwraps the known prefixes; a keyword, `[`, `test`, `exit` or a group ends the walk. `targets` reads the operands of the table commands (`SPECS`: each command's short and long options); an option the table lacks, or a word that could expand into one, gives none. `shellWrites` walks the list: `&&` keeps going, `;` and a newline also commit, `||` also proposes its right side for the disk check, and a list sent to the background with `&` is dropped. Directory changes on either side of `||` leave later relative paths unknown. A later absolute `cd` followed by `&&` can establish the directory again. A newline directly after `||`, `&&` or a pipe continues that command. The rules and what is skipped are in [Files and runtime limits](../feasibility/files.md).

### Git worktrees: `hooks/sources/worktrees.ts`

Writes no items: it keeps the repository's worktrees in the `$.state` key `rabe.worktrees` (`RabeWorktree[]`: `path`, `branch?`, `isDetached?`, `isMain?`), so the Effects tab can place each changed file in the worktree that holds it.

| Hook | What it does |
|---|---|
| `session.start` `{ isInteractive: true }` | Runs `git worktree list --porcelain` through `$.process.run` (in the session's folder, 5 s timeout) at session start and then through the shared loop every 10 s. The shared loop skips a tick while a pass runs. `parseWorktrees` reads the blocks: the first is the main worktree (`isMain`), `branch refs/heads/x` gives `x`, `detached` sets `isDetached`; a bare entry, a path git had to quote and a relative path are left out, and at most 100 are kept. The list is written only when it changed. A run that fails, cannot start (no git, the desktop), exits with another code than 0 (not a repository), is cut at 4 MiB or lists nothing writes nothing, so the last known list stays, and without one the views keep their behaviour from agent metadata. |


## Output path checks

`taskFolder(path, sessionId, projectRoot)` in `hooks/tasks.ts` accepts plain output file names for this session and project. It checks the temporary task layout. The project folder encodes `$.session.root()` with non-alphanumeric characters replaced by `-`. Shells and monitors call it before every output read, including polls, notifications and Stop correction. They stat the file and folder with `{ resolve: true }`. The file must resolve to that folder plus its file name. They read the resolved path after this check. Missing resolutions or unexpected paths give no output. Large shell output follows the same check before `tail`.

## Testing sources

The test's `$` has no `state` noun. `memoryState(on)` from `hooks/testing.ts` answers `state.get` and `state.set` from memory, with versions, and returns the record to read (`state['rabe.items'].value`). `files(on, held, log?)` answers file stats, whole reads, inode commands and byte-tail commands from a record. The optional log records `read <path>` and `tail +N <path>`. `core(on)` answers the events the tests raise that nothing beneath the plugins answers: `prompt.submit`, `session.start`, `command.register` and `classic.Stop`. Tool results come from a test hook on `tool.call`, and `mock.clock` drives the poll.
